# Kyro Security

Kyro is a **non-custodial** wallet: nobody but you has your keys, not even the developers. This document honestly explains what Kyro protects, how, and what **no software** can protect.

> Version 0.1 — **unaudited software, under development, testnet by default.** Do not put in money you cannot afford to lose until an external audit has been published. **No native confirmation window has yet been clicked by a human in the real application**: the real test sends went through the same Rust functions, without an interface (see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)).

## Reporting a vulnerability

Do not publish the vulnerability in a public issue. Write to the address given in the project's GitHub profile (section *Security → Report a vulnerability*), with a proof of concept if possible. Acknowledgement within 72 h; fix and coordinated disclosure within 90 days at most.

## Security architecture

```
 React interface (webview)     ─ no secrets, no direct network access
        │ invoke() — Tauri command allowlist
 Tauri shell (Rust)            ─ session, auto-lock, filtered network, native confirmation dialog
        │
 wallet-core (pure Rust)       ─ encryption, derivation, signing; no network, no files
```

| Measure | Detail |
|---|---|
| Encryption at rest | Recovery phrase encrypted with **XChaCha20-Poly1305**; key derived from the password by **Argon2id** (256 MiB, 3 passes, 4 lanes). The header (version, parameters, salt) is authenticated: any modification makes decryption fail. **Floor** of 64 MiB and 2 passes, **ceiling** of 1 GiB, 10 passes and 16 lanes, checked by wallet-core at creation **and** at opening, before any derivation: a weaker vault is **refused** (not re-encrypted: Kyro has never written one, so it can only come from another tool or from tampering). The weak test parameters exist only in wallet-core's unit tests. The vault is created under a lock (two simultaneous creations cannot both succeed) and **never overwrites** an existing vault. |
| Secrets in memory | `Zeroizing` types: phrase, seed and keys are wiped from memory after use. Private keys are derived **at every signature** (the vault is decrypted again with the password) and then wiped; the seed (and, for Cardano, the Icarus root) is kept only during the unlocked session, because it is used to derive the public addresses (see "Known limitations"). Wiping is **best effort**: secp256k1 keys (`SecretKey`, a `Copy` type) are borrowed from the guard that wipes them, never copied into Kyro's code (TRON, XRP fixed on 2026-11-01); the Icarus root is bounded in place and the Cardano hashing prefix is filled in place. What remains out of Kyro's reach are the copies made **inside** the libraries (by-value argument of `Scalar::from_bytes_mod_order`, `XPrv` constructors, libsecp256k1 stacks) and what the compiler keeps in registers. |
| Signing | **Only in Rust.** Every signature requires the password (re-verified by Argon2id) **and** a confirmation in a **native system window**, which shows the summary decoded by Rust — not by the interface. A token's name and decimals come **only** from Rust's table (`known_tokens.rs`) or from a verified Ledger descriptor: a token not in the table is displayed in raw units, "UNKNOWN TOKEN". Any free text (memo, account name, validator name, pool name…) is put on a single line, between "…", without control, bidi or invisible characters, and memos come after the amounts: it cannot add a fake "To:" line. Anything unknown or unusual triggers a **2nd reinforced window**, on all chains (Bitcoin, EVM, Solana, Litecoin, Dogecoin, Zcash, TRON, XRP, Cardano, Stellar, NEAR, Sui, Hedera, Kaspa, Monero, Aptos) and on hardware wallets (triggers: see each chain); on Polkadot, nothing unusual is accepted (refusal). |
| Password | 5 free attempts, then an increasing delay (30 s to 15 min). Each attempt is counted **before** the Argon2id computation, under the same lock as the delay check (parallel attempts do not get around the limit), and the counter is saved next to the vault: restarting Kyro does not reset it to zero. |
| Auto-lock | Lock after inactivity (15 min by default), on close, and **on wake-up after sleep or hibernation** (detected by a clock jump, on all systems); the session is wiped. Limitation: Kyro does not lock *before* sleep (it does not listen to the system's power events): during sleep, the seed stays in memory (or, in hibernation, in the hibernation file on the disk). |
| Interface | Strict CSP, no remote scripts, no remote fonts or images, no personal data collected (only the anonymous weekly count, see below). Tauri command allowlist (least privilege), no access to the file system or the shell, no direct access to native windows (only Rust opens the dialogs and the file picker). **Navigation guard**: the webview can only load the app's pages (`location.href = "https://…"` is refused) and cannot open any new window (`window.open` refused). |
| Built-in Tor | By default, all network traffic goes through **Tor** (embedded Arti client, end-to-end TLS up to the server): servers do not see your IP, and each activity family (Bitcoin, Litecoin, Dogecoin, Zcash, TRON, XRP, TON, Stellar, Cardano, NEAR, Sui, Hedera, Kaspa, Polkadot, Algorand, Monero, Aptos, EVM, Solana, market, swap) has its own isolated circuits. Bitcoin goes through mempool's official onion service (no exit relay). **Fail closed**: if Tor is not ready, no request goes out in clear. Clear mode is an explicit choice. Servers still see the addresses requested (see [docs/NETWORK.md](docs/NETWORK.md)). |
| Custom servers | Each chain (except Kaspa, for now: default public API only) can use your own server (Esplora, Electrum, Bitcoin Core, EVM/Solana RPC, Litecoin/Dogecoin/Bitcoin Cash/Dash Esplora, java-tron, rippled, Koios), checked at registration (right network) and **with no silent fallback** to the default server. **Each new host** (registration, connection test, reading of an Electrum certificate) is first shown in a **native system window** (usage, host and port): nothing is sent — not even a DNS request — until you have allowed it. Disabling Tor also requires a native confirmation. Electrum: certificate validated, or **pinned** by its SHA-256 fingerprint (confirmed by you at the first connection); never an unvalidated and unpinned certificate. Bitcoin Core: **watch-only** wallet with no private key (public descriptors only). |
| Bitcoin compact filters (BIP157/158, `cbf` function, disabled by default until reviewed) | Your addresses never leave your machine: the filters are compared locally. With Tor enabled, the P2P library has **no** direct outbound connection: it goes through an internal SOCKS bridge limited to the peers supplied by Kyro (loopback, random port, no DNS), open only during synchronization. Peers see which blocks you download (weak signal, documented). |
| Bitcoin Core RPC credentials | **Prefer the `.cookie` file** of your node, **local or on your local network**: Kyro re-reads it on every request and does not copy it. It is chosen in the **system file picker** (opened by Rust, not a path typed in the interface); it must be named exactly `.cookie`, not be a symbolic link, be at most 256 bytes and contain `__cookie__:` + 64 hexadecimal characters, and it is sent only to a local or local-network address (never to a remote node or to a `.onion`). Errors quote neither the path nor the system error. For a remote node: `rpcuser`/`rpcpassword`, whose password is **stored in clear** in `settings.json`, in the app's data folder (a file readable by you alone on Linux/macOS; it is never sent back to the interface, which only sees "password saved"): anyone who reads this folder can control your node. |
| API keys (CoinGecko, 0x, TronGrid) | Stored **in clear** in `settings.json` (the app's data folder), like the Core password: anyone who reads this folder can use them on your account with these providers. **Never sent back to the interface**: `settings_get` only gives "key saved: yes / no" (`apiKeysSet`), and a key can only be replaced or erased, not read back. Rust injects them itself as a header **only toward their provider's host** (e.g. TronGrid: `api.trongrid.io` and `nile.trongrid.io`, never a personal node), and removes them if a redirect changes host. Environment keys (`KYRO_…`) follow the same rule. |
| Network | The interface cannot reach any server: everything goes through a Rust command that only allows the domains listed in [docs/NETWORK.md](docs/NETWORK.md) and your servers **authorized in a native window** (HTTPS, no redirect outside the list — redirects are followed by Kyro, an API key never follows to another host —, size and duration capped). |
| Local alerts | Price alerts and « funds received » (Settings › Alerts, off until you set them) are **computed on this device** from the market prices and the history cache Kyro already loads: no request of their own, no server, nothing leaves the device, and the rules stay in the app's local storage. They run while Kyro is open and unlocked. **Why a plugin**: only `tauri-plugin-notification` shows a native notification on Windows, macOS and Linux. It is called **from Rust only** (`alerts.rs`): the webview gets none of the plugin's permissions, the CSP is unchanged, and the only new capability is the `alert_notify` command. This command takes **no free text**: the interface names a fixed template and gives a ticker and a number, checked by Rust (short, no line break, at most 3 letters in a figure), so a compromised interface cannot write a fake warning or a link in a system notification; at most 6 per minute. While balances are hidden, a notification shows no amount. A notification is shown by your system, which may keep it in its notification centre and show it on the lock screen: it then says which coin moved. |
| Fee choice on Send | Slow, Normal or Fast, with the estimated time and cost, on chains with a fee market (Bitcoin, Litecoin, Dogecoin, Bitcoin Cash, Dash, EVM, Solana); chains with fixed fees show none. A custom value lives under Advanced and is **refused** outside safe limits: EVM max fee from the next base fee up to 20 × the live Fast level (at least 100 gwei, never above 10,000 gwei), tip at most the max fee; Bitcoin and Litecoin from the current mempool minimum to 2,000 per vB; Dogecoin 1,000 to 100,000 koinus per byte; Bitcoin Cash and Dash up to 100 per byte; Solana up to 1,000,000,000 µL/CU. These limits are in the interface, against typing mistakes. What protects you is unchanged: the native window shows the real fee decoded by Rust, and a high fee opens the 2nd reinforced window on each chain. |
| Speed up or cancel | From History, on your own pending sends. **Bitcoin and Litecoin (BIP125)**: Kyro's sends are marked replaceable (`nSequence` `0xfffffffd`) from 1.0.7; earlier sends are refused, and Dogecoin, Bitcoin Cash, Dash, Zcash and Monero have no replacement. A replacement reuses **exactly the same inputs**: a speed-up keeps every recipient and amount and takes the extra fee only from your own change (no change, or too little: refused, you can cancel or wait); a cancel sends everything back to one of your addresses. **EVM**: same nonce, both fee fields at least 10% higher; a speed-up changes only the fees, a cancel is a 0-value send to yourself with no data. **Rust checks all of this whatever the interface built** (`utxo_check_replacement`, `evm_check_replacement`), before the native window: the original comes as its raw transaction (txid recomputed) or with its signature (hash recomputed), so a server cannot lie about the fee it paid; marked replaceable, replacement still replaceable, fee at least the old fee + 1 per vB of the replacement, payments unchanged. The native window opens with SPEED UP or CANCEL, the id replaced, the old and new fee and the extra cost, then the usual decoded summary; same password, same 2nd window, same path on Ledger and Trezor. **Already confirmed**: refused before the review and again just before signing, from what the server says; if a server lies, the network rejects the replacement (coins already spent, nonce already used) and nothing is lost. A transaction that another pending one depends on is refused. **Limits**: a cancel is not guaranteed, the original can confirm first, and the recipient may already have seen the payment. Replacing changes the transaction id. Being marked replaceable is visible on the chain, and some services wait for a confirmation before crediting such a payment. |
| Clipboard | After an address is pasted, the address is displayed in blocks (start and end highlighted); if the field changes without you having typed it, sending is blocked. **Limitation**: software that replaces the address in the clipboard **before** the paste ("clipper") is not detected — the field then contains exactly what was pasted. Kyro therefore never displays "identical to what you pasted"; an address that is neither in your address book nor yours is marked "Unknown address: compare it with your source". An address coming from search is treated as typed; an address picked from the address book or "My accounts" is treated as "Picked" (monitored the same way). |
| Address poisoning | The Send screen compares the recipient to **reference addresses** on their **first 4 and last 4 characters** (after the format's own prefix, e.g. `0x`, `tb1q`, `addr_test1`): a different address with the same start and the same end triggers a **blocking red alert**, and continuing requires ticking a box. **Trusted**: your address book, your own accounts, and the recipients of sends **signed and broadcast by this Kyro** (its own registry, by txid). **Never trusted**: what the server's history says — anyone can make an address appear there, even as "sent by you" (`transferFrom(you, lookalike, 0)` on EVM and TRON). The other counterparties in the history serve only as references; those that appear there only through **suspicious** transfers (zero value in either direction, dust: less than 1 in currency or at most 10 × the dust limit on Bitcoin, Litecoin, Dogecoin; EVM transaction whose sender is not you) never become one, and the history shows them as "Suspicious". Being exactly a known address does not exempt it from the comparison with the others: two known addresses that look alike also trigger the alert. The same check applies when you add a contact. |
| Phrase display | **Only in Kyro's protected phrase window, opened by Rust**, at creation as in Settings › Security and for the Monero 25-word phrase (password, then native confirmation, then the words): the main interface never receives the words, even if compromised and even if it knows the password. This window (label `phrase`, `phrase_window.rs`) is **separate from the interface**: its page is written by Rust and served from its own scheme (`kyrophrase`), so it has **its own origin** (the interface cannot read its storage, register a service worker for it or script it) and a **private profile**; the page is served **only to that window** (any other webview gets 403); **no script at all** (CSP `default-src 'none'; script-src 'none'`, style allowed by hash, fonts from the same origin, nothing external; Hide/Show is pure CSS); **no capability** (no IPC command is granted to the `phrase` label); it cannot navigate elsewhere nor open a window; the words are **blurred** until "Show" is clicked or the words are held; the page is wiped from Rust's memory when the window closes. While it is open the main window is disabled (modal) and also protected from capture. **Capture protection** (`content_protected`): on **Windows** (10 2004+) the window is excluded from screenshots, screen recording and screen sharing (`SetWindowDisplayAffinity`, `WDA_EXCLUDEFROMCAPTURE`); on **macOS** it is hidden from most capture tools (`NSWindowSharingNone`; recent macOS versions with ScreenCaptureKit may still capture it); on **Linux** (X11 and Wayland) there is **no** protection. No software protection stops a camera or someone behind you. The check of the 3 words at creation is done by Rust (positions drawn by Rust, 5 attempts). No copy button, words not selectable. An **imported** phrase, on the other hand, is typed in the interface (unavoidable). |
| Swap fees | **Tapered rate** according to the swap's value in dollars (amount × price of the token sold): 5% up to $5, then 2% at $10, 1.2% at $100, 0.9% at $1,000, 0.7% from $10,000 (interpolation on the logarithm of the amount, rounded to the whole bps); 0.9% if the price is unknown; capped at 2.55% for Jupiter and 2.5% for NEAR Intents (their maximums). Already deducted from the displayed amount received ("Service fee included", link to kyrowallet.com/frais opened by Rust, fixed URL); neither the screen nor the confirmation shows the commission. Collected through the provider's official integrator mechanism (no transfer added by Kyro). The rate is computed **once per quote** and this same rate is what Kyro requires back: a quote whose fees differ from what was requested (rate, amount, beneficiary) is refused; a provider that cannot collect them is discarded. Public config: [docs/SWAP_FEES.md](docs/SWAP_FEES.md). |
| Swaps: third-party transaction verified | The aggregator builds the transaction; Kyro decodes it **before** the password. **EVM (0x, LI.FI)**: `to` and the address to authorize must be the provider's official contract on that chain (fixed list: 0x AllowanceHolder, LI.FI Diamond); native value = 0 for a token sale, = the amount for a native sale; Kyro decodes the calldata (0x: `AllowanceHolder.exec` → `Settler.execute`, Settler confirmed by 0x's official registry; LI.FI: `GenericSwapFacetV3`) and requires **recipient = you** and **minimum ≥ announced amount − slippage**; Kyro fee exactly at the rate requested for this quote to the right address. **Jupiter**: the transaction is decoded by Rust, then Kyro accepts only the compute budget, the creation of **your** token accounts, the wrapping / unwrapping of SOL on **your** wSOL account and a single Jupiter route instruction (debited and credited accounts yours, amount, slippage, expected fee account); no transfer, `approve` or other signer. The confirmation shows a **frozen** quote, the maximum network fees and the guaranteed minimum; the new quote taken just before signing is re-verified, refused if the contract changes, and **asked again** if it guarantees less. Simulation: amount received measured when the RPC allows it (`eth_simulateV1`). Custom slippage ≤ 15%. **Cross-chain** (LI.FI, NEAR Intents bridge only): the destination is always **your own account** on the other chain (never a typed address). EVM departure: `NEARIntentsFacet` call decoded (destination chain, your destination address — Solana key or `bc1q` encoded as LI.FI does —, refund to you, minimum, destination token, no call at the destination, Kyro fee). Solana departure: transaction decoded by Rust, then only transfers from your account to the Kyro fee, the LI.FI fee and **one** deposit address (exact total), plus the LI.FI tracking instruction (unknown to Rust → **2nd reinforced window**, the interface lists what was verified). In both cases, **NEAR Intents confirms** before the password that this deposit address delivers to your account, refunds to you, for this amount, this token and at least this minimum. Remaining risk: delivery by the bridge's solvers (otherwise refund). Tracking in the history via `li.quest/v1/status`. |
| NEAR Intents direct swaps (departure BTC, LTC, DOGE, BCH, DASH, ZEC, TRON, XRP, Cardano, Sui, TON, Aptos; arrival on these chains and on Stellar) | **No third-party transaction**: 1Click (`POST /v0/quote`) gives a single-use deposit address. Before the password, Kyro requires, in the quote **and** in `/v0/status` of this address (read from 1Click): arrival on **your own account** on the other chain, refund to **your** departure address, `EXACT_INPUT`, amount = your input, requested tokens, minimum ≥ announced − slippage, `SIMPLE` deposit (**no memo, no OP_RETURN, no tag**), deposit address ≠ yours, status "awaiting deposit", ≥ 2 h before the deadline, and Kyro fee **exactly at the quote's rate** to the NEAR Intents account of `recipients.evm` (1Click's share ≤ this rate), otherwise refusal. Kyro then builds **itself** an ordinary send of this amount to this address with the chain's adapter, and refuses anything that is not a single payment to it (BTC / LTC / DOGE / BCH / DASH: no OP_RETURN output or unknown script, the rest as change; ZEC: a transparent `t1…` payment, no TEX address; TRON: TRX or TRC-20 transfer of the right contract, no memo; XRP: no tag, memo or path, refusal if the address requires a tag; Cardano: ADA only, no message; Sui / Aptos: a simple SUI / APT transfer; TON: no comment, not "entire balance"; EVM / Solana: identical Rust decoding `evm_decode_tx` / `sol_decode_tx`). Stellar is only an **arrival**: 1Click requires a memo on a Stellar deposit, Kyro never sends one. Rust's native window shows this simple send (an OP_RETURN output there would trigger the 2nd window). 1Click is re-read just before signing, and the transaction rebuilt and re-verified. Remaining risk: delivery by the solvers (otherwise refund, minus `refundFee`), the ed25519 signature of 1Click quotes is not verified, and 1Click sees your departure and arrival addresses together. |
| Currency input | Send can convert an amount in a currency (EUR, USD, CHF, JPY…) at the CoinGecko price **only if this price is plausible** (≤ 25% difference from the last price seen on this device and from the 7-day median); beyond half of the balance, a warning says so; the verification reminds you that it is the crypto amount that is signed. |
| Refused recipients | Bitcoin: only P2PKH, P2SH, P2WPKH, P2WSH, P2TR (a "future" SegWit address, v2 to v16, is unverifiable and unspendable today). EVM: the null address and the token's own contract. Solana: off-curve address (PDA), program, token account or mint. |
| ERC-20 approvals | **Exact** amount by default in swaps. An unlimited amount requires an explicit action and shows a warning ("UNLIMITED" also in the native window). |
| Supply chain | Dependencies pinned to the exact version (≥ 2 weeks old), lockfiles committed, `cargo audit`, `cargo deny` and `pnpm audit` in CI, 3-day delay before accepting a new npm version, pinned Rust toolchain. |

## Threat model

### What Kyro protects (all chains)

| Threat | Protection |
|---|---|
| Theft of the computer or disk, cloud backup of the app folder | Encrypted vault; without the password, the phrase is inaccessible. Strength depends on **your password**: choose a long one. Note: `settings.json` (API keys, possible Core password) and `hw-accounts-*.json` (xpubs) are **not** encrypted. |
| Compromised interface (XSS via a token name, malicious npm dependency) | The interface has neither secrets nor network. It cannot sign without your password and without the system window, which shows what Rust actually decoded — token names included (Rust table). On TRON, XRP, Stellar, Cardano, NEAR, Sui, Hedera, Polkadot, Monero and Aptos, Rust **builds the transaction itself**: the interface supplies only the recipient and the amount. What is now **enforced by Rust**, even if the interface is compromised: the phrase is displayed only in the separate phrase window (own origin, no script, no IPC); no file can be read via the Bitcoin Core configuration (only a `.cookie` chosen in the system picker); no new server is contacted without your native confirmation, nor is Tor disabled; the page cannot navigate elsewhere or open a window. **What it can still do**: see your password when you type it (it is entered in the interface), show you fake balances or a fake history, offer you a booby-trapped transaction (which the native window describes faithfully: read it), see the phrase you import, and — if you allow it in the native window — use a server it has chosen. |
| Software that replaces addresses in the clipboard | Monitoring of the field after the paste, address displayed in blocks, address book, "Unknown address" for any address outside the address book. **Limitation**: a replacement **before** the paste cannot be seen; only the comparison with your source (or the address book) detects it. |
| Address poisoning (a lookalike address slipped into your history by a dust transaction, a zero-value one, or a `transferFrom` at 0 displayed as "sent") | Blocking red alert if the recipient has the same first 4 and last 4 characters as a reference address without being identical; only the address book, your accounts and the sends signed by this Kyro are trusted, never the server's history. Limitations: a lookalike that already differs within these 8 characters is not detected — check the whole address, or copy it from Receive or the address book; a lookalike that you have already paid once from Kyro, or saved to the address book despite the alert, becomes a trusted address (the other known addresses that resemble it keep triggering the alert). |
| Booby-trapped text coming from the chain (memo, CIP-20 message, Solana seed, Cardano token name): line breaks that push the real content out of the window, bidi characters (`U+202E` reverses the text) or invisible ones | In wallet-core, **a single sanitizer** for the decoders (`sanitize_text`, exported for the shell): control characters replaced (`\n` `\r` `\t` by a space), bidi / invisible (`U+200B`–`U+200F`, `U+202A`–`U+202E`, `U+2060`–`U+206F`, `U+FEFF`, tags…) removed, length bounded with "…". Any modified text adds a warning and the **2nd window**; a Cardano token name that needs sanitizing is shown only in hexadecimal. On the shell side, **all** text of the native window goes, just before display, through `dialog_text.rs`, under the same rules (memos, account, validator, pool, SR and device names, server hosts; see "Signing"). The names and decimals of EVM, SPL and TRC-20 tokens no longer come from the chain or from the interface, only from Rust's table (`known_tokens.rs`). **Limitation**: `dialog_text.rs` does not yet call `sanitize_text`: these are two implementations of the same rules, to be merged. |
| Prying eyes or capture while the phrase is displayed | Warning, separate phrase window (outside the interface), words blurred until shown, no copy, excluded from screenshots and screen sharing on Windows (and most capture on macOS). Not on Linux, and never from a camera: check that nobody is watching. |
| Booby-trapped update (compromised GitHub account, CDN, Tor exit relay, modified `latest.json`) | **Signed** automatic updates: each package is verified (minisign Ed25519, `minisign-verify` crate, the one used by tauri-plugin-updater) with the public key **pinned** in the binary (`tauri.conf.json` → `plugins.updater.pubkey`); the private key exists only outside the repository and in the CI secrets. See "Automatic updates" below. |
| Server that lies | See each chain: in general a server can lie about **what you own and what happened** (balance, history, existence of an account), not about **what you sign**, which Rust decodes itself. To be sure of your balance: your own node. |

### What no software can protect

- **Malware with full control of your machine while the vault is unlocked.** It can read memory, record your keystrokes (hence your password), display a fake window and drive the application. This is the limit of every software wallet.
- **A keylogger + a copy of the vault file**: with both, the vault can be opened.
- A compromised operating system, firmware or hardware.
- You giving away your recovery phrase (fake support, fake site, fake "airdrop"). **Nobody legitimate will ever ask you for it.**
- You confirming a transaction you have not read: the native window only protects if you read it.
- Physical coercion.

**Hence our recommendation: use a hardware wallet** (Ledger, Trezor) once this has been tested. The keys stay in the device and each transaction is verified on its screen, even if the computer is infected. *(Code written, tested against recorded exchanges and simulations, **not yet against a real device or an emulator**: see below.)*

## Threat model per chain

For each chain: what Rust decodes and refuses before signing; what the server can falsify and what that changes; the scams specific to the chain; what remains at risk.

### Bitcoin (BIP84 SegWit, BIP86 Taproot)

- **Rust decodes and refuses.** The PSBT is decoded by rust-bitcoin; each input must carry `witness_utxo` (and `non_witness_utxo`, if present, must match the outpoint); the derived key must be the one of the PSBT and of the spent script; only `SIGHASH_ALL` / `SIGHASH_DEFAULT` are signed; negative fees and overflows refused; inputs that are not ours are not signed. Change is recognized on 20 receiving addresses and 20 change addresses per type. A non-standard output is displayed as `script:<hex>` or `op_return:<hex>`; this is also the case for a witness program **v2 or higher** (reserved for future soft forks) and for a v1 that is not a 32-byte taproot, instead of an ordinary-looking `bc1z…` address. An output to one of our keys is **change** only up to address index **1000** (`MAX_CHANGE_INDEX`): beyond that, it is displayed as a payment (no wallet that sweeps with a gap limit would find these coins again).
- **The server can lie about**: the balance, the history, the UTXOs (nonexistent coins: the transaction is then simply rejected by the network), the suggested fees (fees too high: **displayed** in the native window before signing). It cannot change the amount of a SegWit input without changing what Rust displays, since the sighash commits to this amount.
- **Scams.** Address poisoning (an address resembling yours slipped into the history by a small transaction): the Send screen's **address-poisoning alert** applies (see "What Kyro protects"); still copy from the Receive screen or the address book, never from the history. Dust scam (small coins sent to track you): Kyro does not freeze these coins.
- **2nd reinforced window** (vault and hardware wallet): output with unknown script, OP_RETURN, input that is not ours (not signed by Kyro: coinjoin, payjoin or trap), fees above **100 sat/vB** (100 × the relay minimum) or greater than the total of the outputs, output to our keys beyond index 1000. A sighash other than ALL / DEFAULT on our inputs is **refused**, not merely flagged. The displayed summary is computed like the one used for signing and must be identical to it.
- **Residual risks.** "SegWit fee bug": `non_witness_utxo` is not required, so two manipulated signing sessions could make you pay unexpected fees; each session remains confirmed separately. **No real testnet broadcast has yet been made from Kyro**: the public test wallets ("abandon … about" and Trezor "all × 12", BIP84 and BIP86, 20 receiving addresses and 20 change addresses each) have no testnet4 coins (verified via Tor on 2026-10-30), and testnet4 faucets ask for a captcha.

### Ethereum and EVM chains (Arbitrum, Optimism, Base, Polygon, BNB Chain, Avalanche…)

- **Rust decodes and refuses.** EIP-1559 transactions only (no contract creation); **a single list** of known chain ids in wallet-core (`EVM_KNOWN_CHAINS`, with their family: mainnet 1, 42161, 10, 8453, 137, 56, 43114, 25, 5000, 146, 14, 8217, 100, 999, 1329, 1030; test 11155111; Ethereum Classic, 61, is not part of it: its pool rejects type 2 transactions); both decoding **and** signing receive the wallet's network and **refuse** a chain id from the other family (a test-mode wallet never signs for a mainnet network, and vice versa). Rust recognizes native transfers, ERC-20 `transfer` and ERC-20 `approve` (amount, spender, **"UNLIMITED"** from 2^128, same rule for the summary and the warning); anything else is displayed as "Contract call: address, value sent". The window shows the network (known name or "chain N", signed chain id) and the **maximum fees** (gas limit × max fee). No message signing or typed data (EIP-712): a "permit" cannot be signed by Kyro.
- **The server (RPC) can lie about**: native and ERC-20 balances, nonce (stuck or replaced transaction), gas estimate and price (fees too high, but capped by the displayed maximum; the tip read from the RPC is additionally bounded: ≤ 3 × the lower level and ≤ 3 × the base fees + 2 gwei), simulation result (`eth_call`: a false "it passes"). The symbol and decimals shown by the native window come **neither from the server nor from the interface**: only from Rust's table (`known_tokens.rs`, per network, chainId and contract); a token not in the table is displayed in raw units, "UNKNOWN TOKEN", with the 2nd window. The contract and the raw amount come from Rust.
- **Scams.** **Unlimited approvals** (`approve` max): flagged "UNLIMITED" with a warning; exact amount by default in swaps. Fake tokens with the same symbol: only the contract matters; Kyro's list is fixed (registry `registry.ts`, contracts and decimals verified on-chain, copied into the generated Rust table). Address poisoning (0-token transfers from a lookalike address, and `transferFrom(you, lookalike, 0)` which anyone can call and which appears as "sent by you"): the **address poisoning alert** on the Send screen applies (see "What Kyro protects"); any 0 transfer is suspect by default, and an "outgoing" transfer whose transaction was not sent by you is flagged "not signed by you". Null address and the token contract are refused as recipients.
- **Hardened 2nd window** (vault and hardware wallet): any contract call other than a decoded ERC-20 `transfer`; an ERC-20 `transfer` of a token **unknown** to Kyro; **any** authorization (`approve`), with the beneficiary and the amount ("UNLIMITED" in capitals from 2^128); native value sent with a call; chainId unknown to Kyro; maximum fees (gas limit × max fee) above **0.05** of the native currency (ETH, L2 ETH, BNB, HYPE), **50 POL** on Polygon, **1 AVAX** on Avalanche, about 10 USD on chains with a cheap currency (200 CRO, 20 MNT, 250 S, 2,000 FLR, 300 KAIA, 10 XDAI, 200 SEI, 200 CFX; `evm_high_fee_threshold_wei`).
- **Residual risks.** For a contract call, Rust **does not decode the calldata**: signing an unknown call amounts to trusting the application that built it. For swaps, it is the interface (TypeScript) that decodes the 0x and LI.FI calldata and refuses what does not match (see "Swaps: third-party transaction verified"); a compromised interface could skip this check, the native window then showing only "Contract call" to the called address. The simulation is performed by the RPC, which can lie; the minimum written in the calldata is still enforced by the contract. A value transfer **without** calldata to an address that happens to be a contract is not detected (Rust does not query the RPC to sign). **No real broadcast on Sepolia or on an L2 testnet**: no public test wallet has any Sepolia ETH (checked on 30/10/2026: "abandon … about", Hardhat "test … junk" — 0.000000000000188 ETH, unusable —, Trezor "all × 12"); faucets require a captcha or a mainnet balance; L2 testnets are not in Kyro's registry. The signature is verified against a real mainnet transaction.

### Solana (SOL, SPL, Token-2022)

- **Rust decodes and refuses.** Legacy and v0 messages are decoded in Rust; address lookup tables (ALTs) are read **by Rust** from the RPC and verified (owner, not deactivated, indexes present); fails closed if a table is missing. Each address that is not written in the signed message but comes from a table is **flagged** in the native window ("[read from an address table]") and forces the **2nd window** as soon as a recognized instruction uses it (recipient, authority, token account…); staking refuses them. The mint is named by Rust's table, otherwise "unknown token". Recognized instructions: System transfers, account creation, SPL / Token-2022 transfers and `approve`, ATA creation, compute budget, memo, and four instructions of the Stake program (see "Staking" below). Everything else is "unknown", **except** the Stake program: any other staking instruction (authority change, lockup, split, merge…) is **refused**, not merely flagged. **Hardened 2nd confirmation** if: unknown instruction, **delegation** (`approve`), fee payer ≠ us, another writable signer, authority ≠ us, **account creation** (`CreateAccount` / `CreateAccountWithSeed`) for an owner program outside the closed list (System; Token with the size of a token account or a mint; Token-2022 with the size of a mint or of an account from 165 to 1024 bytes; Stake, verified separately) — "the created account belongs to an unknown program: it will be able to spend these SOL" —, **unchecked SPL `Transfer`** (tag 3, without mint or decimals; only `TransferChecked` passes without a 2nd window), **memo** that was sanitized or longer than 80 characters (a sanitized seed too). Refuses if our address is not a signer.
- **The server can lie about**: balances, token accounts, decimals of a mint, **contents of the address lookup tables** (a fake table changes the displayed accounts: Rust verifies the format and the owner of the table account, not that its contents match the chain; these accounts are therefore flagged and hardened, see above; with your own RPC, this risk disappears; a change of RPC by the interface requires your native confirmation), recent blockhash (expired transaction), priority fees.
- **Scams.** Recipient that is not a wallet (off-curve address / PDA, program, token account or mint): refused at construction. 0-lamport transfer from a lookalike: neither received nor sent, flagged suspect, the counterparty comes from the decoded instructions (never from the fee payer). Jupiter swap, and cross-chain swap departing from Solana (LI.FI): third-party transaction verified before the password (see "Swaps: third-party transaction verified"). **Delegation** of tokens to a third party (`approve`): hardened. **Durable nonce** (`AdvanceNonceAccount`): a signed transaction remains valid indefinitely and can be broadcast later; Kyro does not recognize it (unknown instruction → hardened) and builds its own with a recent blockhash. Ownership change (`Assign`, `SetAuthority`): unknown → hardened. Fake tokens with the same name: only the mint matters.
- **Residual risks.** Token-2022 extensions (transfer fees, hooks) are not verified: flagged, without a 2nd window. Decoding is tested on 6 real devnet transactions and 9,000 mutated messages, and **7 real devnet transactions** went through the Rust path of `sol_sign_tx` (SOL, SPL and Token-2022, address lookup table, v0 transaction whose table was read by Rust); these messages were built by the test, not by the TypeScript adapter.

### Litecoin (BIP84 `ltc1`)

- **Rust decodes and refuses.** Like Bitcoin (rust-bitcoin, `witness_utxo` required, BIP143, key = script, sighash ≠ ALL refused); Bitcoin addresses (`bc1…`, `1…`) and the old P2SH `3…` refused, MWEB refused. Fees, rate and size computed by Rust. **Unknown output (including witness v2+), OP_RETURN, foreign input, excessive fees, output to our keys beyond index 1000 (not counted as change) → hardened 2nd window**; output below dust refused.
- **The server (litecoinspace.org or your own) can lie about**: balance, history, UTXOs, recommended fees (displayed before signing), raw transaction of an input (verified by its txid).
- **Scams.** Bitcoin address pasted by mistake: refused. Address poisoning: the **address poisoning alert** on the Send screen applies (see "What Kyro protects").
- **Residual risks.** Same "SegWit fee bug" as Bitcoin. **Testnet**: the SLIP-44 convention (coin type 1) gives Litecoin testnet the **same keys** as Bitcoin testnet BIP84; a Bitcoin testnet PSBT presented to `ltc_sign_psbt` would be signed (displayed as `tltc1…`). Worthless on testnet, but these addresses are linkable across testnets. On mainnet, the paths differ (`84'/0'` / `84'/2'`).

### Dogecoin (BIP44 P2PKH)

- **Rule: amounts and scripts are taken only from the verified previous transaction.** The legacy sighash does not commit to the amounts: a server that inflated the amount of a coin could have enormous fees signed without the signature "seeing" it. Therefore, **before any signing**, for each input, Rust (`wallet-core`, `utxo_sign_psbt` / `utxo_psbt_summary`) requires the **complete previous transaction** (`non_witness_utxo`), recomputes its hash and refuses if it differs from the outpoint's txid, if the `vout` does not exist, or if the script of that output is not that of our key. The input amount — hence the **fees displayed in the native window** — comes from that transaction, **never** from the server's UTXO list. Failure → clear refusal (`INVALID_INPUT`), no window, no signature. On the read side, the Electrum backend performs the same cross-check for each announced UTXO (hash, output, our script, exact amount) and refuses the entire list at the slightest discrepancy. Regression tests (`crates/wallet-core/tests/utxo.rs`, `apps/desktop/src-tauri/src/utxo_backend.rs`, recorded real responses): lying amount → actual fees recomputed and 2nd window, or list refused; previous transaction with the wrong hash → refusal; output that does not pay our address → refusal. Litecoin: only P2WPKH inputs are signed (BIP143 commits to the amount); if a previous transaction is also provided, it must match `witness_utxo`, and a legacy coin (P2PKH) is never signed.
- **Rust decodes and refuses.** Fees by size (Dogecoin Core 1.14.9 rules: 0.01 DOGE/kB recommended = Kyro's minimum, relay 0.001 DOGE/kB), server estimates bounded to [0.01; 1] DOGE/kB, hard dust (0.001 DOGE) refused, **soft dust, unknown output, excessive fees (> 1 DOGE/kB or > amount sent), change beyond index 1000 → hardened 2nd window**.
- **Default server (mainnet) and trust model.** The public ElectrumX servers of **Komodo Platform** (`doge.electrum1.cipig.net`, fallback `doge.electrum2.cipig.net`, TLS port 20060, certificate validated normally, genesis verified at each session, over Tor by default). They see your addresses (script hashes) and your transactions, the IP of a Tor exit relay (your IP in clear mode). **They can lie about** the displayed balance and history, **hide** coins or transactions, refuse or delay a broadcast, and give fee estimates (bounded). **They cannot** make you sign an amount or fees different from those in the native window (see the rule above), nor inject into the history a transaction that does not touch your address, nor pose as another network (genesis). Testnet: **no default server**, you need your own (Dogecoin Esplora). Your server replaces the default, with no fallback.
- **Scams.** Same as Litecoin.
- **Residual risks.** Mainnet reads verified live (in clear, captured responses passed through Kyro's parsers) on public addresses; the full test over Tor has not yet been run to completion; **no real mainnet broadcast** by Kyro (no test Dogecoin on mainnet, no public testnet server). A single operator (Komodo) for the two default servers. Testnet: keys identical to Bitcoin testnet BIP44 (same SLIP-44 convention as above).

### Bitcoin Cash (BIP44 P2PKH, CashAddr)

- **CashAddr addresses only.** `bitcoincash:q…` (chipnet `bchtest:q…`), optional prefix, checksum verified (all the specification's vectors, in Rust and in TypeScript). The legacy form `1…` / `3…` is **refused**: it is indistinguishable from a Bitcoin address, and a copy-paste error would send BTC or BCH to the wrong place.
- **`SIGHASH_ALL|FORKID` (0x41) signature.** BIP143 digest (it commits to the amount of each signed input), computed by the audited BIP143 encoder of the `bitcoin` crate of which only the "type" field is replaced; verified on the 236 FORKID vectors of Bitcoin Cash Node, on a real mainnet transaction, and by the Trezor `test_bcash.py` tests: **the transaction signed by Kyro is identical, byte for byte, to that of the Trezor firmware** (RFC 6979 signatures). A FORKID signature does not fit in a PSBT partial signature: Rust finalizes the input itself.
- **Same rule as Dogecoin, as a precaution**: each input must carry its complete previous transaction (hash verified), amount and script come from there, never from the server. Transaction version 1 or 2 only (consensus rule since May 2023).
- **Default servers**: public Fulcrum servers from three operators (`bch.imaginary.cash`, fallback `bch.loping.net`, `cashnode.bch.ninja`; chipnet `chipnet.imaginary.cash`, `chipnet.bch.ninja`), TLS validated, over Tor by default. **Bitcoin Cash shares Bitcoin's genesis block**: Kyro also verifies, at each session, the hash of block 478,559 (first block after the split), recomputed by Rust; a Bitcoin server is refused — otherwise it could display the Bitcoin balances of an address with the same hash. They can lie about the balance and history, hide coins, refuse a broadcast, give fee estimates (bounded to [1; 100] sat/B); they cannot make you sign any amount other than that of the native window.
- **CashTokens**: coins that carry tokens are excluded (`exclude_tokens`) and, if a server slipped one in, its script would not be ours (token prefix): list refused, signature refused. Kyro therefore never burns tokens… and does not display them either (no CashTokens support).
- **Residual risks**: no real broadcast (neither chipnet nor mainnet) by Kyro; mainnet reads verified live (see NETWORK.md); no personal Electrum server possible for now (Esplora only, rare for BCH). Chipnet: same keys as Bitcoin testnet BIP44 (coin type 1).

### Dash (BIP44 P2PKH)

- **Legacy sighash: the Dogecoin rule applies as is**: complete previous transaction mandatory for each input, recomputed hash = outpoint's txid, existing output, script = ours, **amount taken only from that transaction**; otherwise refusal before any window. Tests: Trezor `test_dash.py` vectors (signed transaction identical byte for byte), real mainnet transaction, lying amount → actual fees + 2nd window, forged previous transaction → refusal.
- **Special transactions (DIP2)**: decoded and verified (txid over the full serialization, payload included), displayed in the history, but **never signed** (a PSBT of type ≠ 0 is refused) and their coins **never spent** (`dash_tx_hex` refuses, `dash_address_utxos` discards them): the PSBT cannot carry their payload, so Kyro could not prove their amount. Consequence: a coinbase reward or a Platform withdrawal received on a Kyro address is not spendable from Kyro (it remains visible in the balance).
- **Default server (mainnet)**: Komodo's ElectrumX (`dash.electrum1.cipig.net`, fallback `dash.electrum2.cipig.net`, TLS 20061), same trust model as Dogecoin; testnet: no public server, you need your own. No PrivateSend/CoinJoin or InstantSend requested: a classic send.
- **Residual risks**: no real broadcast by Kyro; a single operator (Komodo) for the two default servers.

### Zcash (transparent addresses only)

- **What is supported.** **Transparent** addresses (`t1…` P2PKH, BIP44 `m/44'/133'/a'`), and as recipients also `t3…` (P2SH) and `tex1…` (ZIP 320). A transparent address is **as public as a Bitcoin address**: amounts, counterparties and history are visible to everyone. **Shielded** (`zs…`, `zc…`) and **unified** (`u1…`) addresses are **refused** by Rust ("not yet supported") and the interface says so beforehand; Kyro does not see the shielded funds of another wallet, even one derived from the same phrase.
- **Rust builds and decodes.** Kyro **builds the v5 transaction itself** with the official librustzcash crates (`zcash_primitives`, `zcash_transparent`, `zcash_protocol`): the interface only proposes coins (outpoint + index of our address, **without an amount**), the recipient and the amount. For each coin, Rust reads the **complete previous transaction**, re-parses it and recomputes its txid; the output must pay the account's key at the announced index; amount and script come from that transaction. Mined coins (coinbase) refused. **ZIP 317** fees computed by Rust; change to **our** address (`…/1/i`, i ≤ 1000); change below 5,000 zatoshis added to the fees (stated in the window). `SIGHASH_ALL` signature over the **ZIP 244 digest** (computed by `zcash_primitives`, it commits to the amount and script of each input: a server that inflates an amount can only get the transaction rejected), ECDSA libsecp256k1, low-S, each signature verified, final encoding re-read and compared with the window's summary.
- **Network upgrade (consensus branch).** Rust **reads it from the chain** (header of a v5+ transaction from one of the last 3 blocks) and signs only if it is known to its version of `zcash_protocol` **and** equal to what its activation table gives for that height; otherwise: clear refusal ("update Kyro"). Never a hard-coded branch. **Known limitation**: the table of the embedded version (`zcash_protocol` 0.11.0-pre.1, the latest published for over 2 weeks) **has no mainnet height for NU7**; as soon as the network has moved to NU7, Kyro will refuse to send ZEC (no funds at stake) until the crates are updated (0.31.0 / 0.11.0, which give NU7 at block 3,543,405).
- **Hardened 2nd window**: fees > 10 × the ZIP 317 fees, or greater than the amount sent; "unknown" signing account.
- **Default server and trust model.** The public ElectrumX servers of **Komodo Platform** (`zec.electrum1.cipig.net`, fallback `zec.electrum2.cipig.net`, TLS port 20058, certificate validated normally, genesis verified at each session, over Tor by default, `zcash` family). They see your transparent addresses (script hashes) and your transactions. **They can lie about** the displayed balance and history, hide coins, refuse a broadcast, announce a false height or branch (the transaction is then rejected by the network). **They cannot** make you sign a recipient, amount or fees other than those in the native window. Testnet: **no server** (no public Zcash testnet ElectrumX).
- **Scams.** Address poisoning: the Send screen's alert applies (`t1`/`t3` prefix excluded from the comparison). Shielded or unified address pasted by mistake: refused with a clear message, nothing is built. TEX (`tex1…`, often an exchange platform): paid as P2PKH of the same key, the window displays the corresponding `t1…` address.
- **Residual risks.** **No real broadcast** has yet been made by Kyro (neither mainnet nor testnet: no testnet server); the signature is verified against a **real mainnet v5 transaction** signed by another wallet (Kyro's ZIP 244 digest = the one the network accepted) and the encoding against `zcash_primitives`; mainnet reads verified live in clear, not yet via Tor. librustzcash crates in **pre-release** version (0.31.0-pre.2), chosen because the 0.30 line cannot coexist with Arti (`crypto-common`) and 0.31.0 is less than 2 weeks old. A single operator (Komodo) for the two default servers. Hardware wallets: `HW_UNSUPPORTED`.

### TRON (TRX, TRC-20)

- **Rust decodes and refuses.** Kyro **builds `raw_data` itself** (latest block, contract, `fee_limit`); before signing, a strict protobuf decoder with byte-for-byte identical re-encoding. Refused: any contract other than TRX transfer and contract call — hence **permission change** (`AccountPermissionUpdate`) and **resource delegation** to another account; freeze, unfreeze, vote and rewards go only through the Staking path (below) —, `Permission_id`, another owner, `auths`/`scripts`, TRC-10 value, expiration in the past or more than 24 h away (the 24 h cap is checked **by wallet-core itself**, on the system clock, at decoding and therefore at signing — payment as well as staking). **Hardened 2nd window**: call that is not `transfer(address,uint256)` (hence **`approve`**), transfer of a token **unknown** to Kyro, TRX sent to the contract, memo (displayed sanitized, `memoText`), `fee_limit` > 100 TRX.
- **The server (TronGrid or your own) can lie about**: TRX and USDT balances, history, resources (bandwidth, energy), **energy simulation** of a TRC-20 transfer (underestimated: you burn more TRX than expected, **never more than the displayed `fee_limit`**, a hard protocol cap), existence of the recipient account (activation cost 1 TRX + 0.1 TRX displayed or not), reference block (transaction rejected).
- **Scams.** **Permission change** (multisig takeover of the account, the most common TRON scam): impossible to sign. **Unlimited TRC-20 `approve`**: hardened. Fake USDT: only the contract matters; Kyro names only the official USDT (and Nile's test USDT). Address poisoning (0 USDT transfers from lookalikes): very widespread on TRON; the **address poisoning alert** on the Send screen applies (see "What Kyro protects"), and these 0 senders are suspect by default.
- **Residual risks.** An unknown TRC-20 token is displayed in raw units, "UNKNOWN TOKEN", with the 2nd window (the interface can no longer name it). One address per account (`m/44'/195'/a'/0/0`, account 0 = `m/44'/195'/0'/0/0`, see "Multiple accounts").

### XRP Ledger (XRP, issued currencies)

- **Rust decodes and refuses.** Kyro **builds the Payment itself** (sequence, fees, ledger limit read from the server, wallet-core binary codec); strict decoding with identical re-encoding: **only Payments** from our account with our key — never AccountSet, **SetRegularKey**, **SignerListSet** (account takeover), TrustSet, offers, escrow…; `Paths`, `DeliverMin`, `TicketSequence`, `NetworkID`, unknown fields or flags refused; **`LastLedgerSequence` mandatory** (without it, a signed payment would remain valid indefinitely). **Hardened 2nd window**: SendMax, path options, memo (sanitized text, exact hexadecimal), InvoiceID, fees > 1 XRP. **Low-S** DER signature.
- **The server (rippled) can lie about**: balance, **reserves** (base and per object), **existence** of the recipient account and its **"tag required"** flag (`lsfRequireDestTag`) — a lying server can make you send without a tag to an exchange that requires it (funds stuck with it) or below the reserve to a nonexistent account (payment rejected by the network, fees lost); sequence and fees (transaction rejected or fees displayed higher); the **delivered** amount in the history.
- **Scams.** **Partial payment** (`tfPartialPayment`: the recipient receives almost nothing while Amount shows a large sum; a classic scam against exchanges): **refused at signing**, and the history displays the amount **actually delivered** (`delivered_amount`). **Forgotten destination tag**: boxed in the native window (or "NO DESTINATION TAG"), and refused if the recipient requires one. X-addresses refused (classic address + separate tag, so that the tag is always visible). Fake issued currencies: only the issuer matters.
- **Residual risks.** One address per account (`m/44'/144'/a'/0/0`, account 0 = `m/44'/144'/0'/0/0`). Trust lines read-only.

### Stellar (XLM)

- **Rust decodes and refuses.** Kyro **builds the transaction itself** (sequence, fees and time bounds read from Horizon; XDR written by hand in wallet-core, identical re-encoding required): **a single operation**, either a Payment of XLM or a CreateAccount for a recipient that does not exist yet — never **SetOptions** (adding a signer or changing thresholds: account takeover), AccountMerge (empties the account), ManageData, offers, path payments, claimable balances, sponsoring, clawback, or a Soroban contract; fee bump and v0 envelopes, multiplexed accounts (M…), advanced preconditions, and an operation with its own source are refused. **Time bounds are mandatory** (at most 5 minutes: without them, a signed transaction would stay valid indefinitely). The **network passphrase** is part of what is signed and the native window spells it out in full; Kyro refuses a Horizon that announces a different network, and a testnet signature does not verify on the main network (tested). **Hardened 2nd window**: fees > 0.01 XLM, a "refund"-type memo, a text memo that had to be sanitized or is unreadable. ed25519 signature (`ed25519-dalek`, same SLIP-10 derivation as Solana), verified before being returned.
- **The server (the SDF's Horizon) can lie about**: balance, **reserve** (base reserve, number of entries), **existence** of the recipient account (Payment or CreateAccount: the network rejects the wrong operation, 100 stroops of fees lost) and its **required memo** (`config.memo_required`, SEP-0029: a lying server can make you send without a memo to a platform that requires one — funds stuck there); sequence and fees (transaction rejected, fees capped at 0.01 XLM); ledger time (time bound too short, or capped at 5 minutes); history.
- **Scams.** **Forgotten memo**: boxed in the native window (or "NO MEMO" (AUCUN MÉMO) with the warning), field always visible, and refused if the recipient requires one. M… addresses are refused (G… address + memo kept separate, so the memo is always visible); a **secret key S…** pasted in place of an address is refused with a warning. Fake "XLM" issued by an account: only native XLM is sent. Address poisoning (one-stroop payments from lookalikes, very common on Stellar): the **address poisoning alert** on the Send screen applies.
- **Residual risks.** One address per account (`m/44'/148'/a'`, account 0 = `m/44'/148'/0'`, SEP-0005). Tokens: Circle's USDC only (known issuer in wallet-core); the trustline (ChangeTrust) is opened and removed by Kyro, with its 0.5 XLM reserve shown; any other asset or issuer is refused at signing. From a hardware account: see "Tokens from a hardware account". No custom Horizon server: the SDF's Horizon only.

### NEAR Protocol (NEAR)

- **Rust builds, decodes and refuses.** Kyro **builds the transaction itself** (access key nonce + 1 and final block read from the RPC, Borsh encoded by wallet-core); strict decoding with identical re-encoding: **a single `Transfer` of NEAR**, from our implicit account, signed by our ed25519 key — never `FunctionCall` (hence no NEP-141 tokens), `AddKey` / `DeleteKey` (account takeover), `DeleteAccount`, `Stake`, `Delegate` (meta-transaction), `DeployContract`, nor multiple actions; `TransactionV1`, another key type, and extra bytes are refused. ed25519 signature over `SHA-256(borsh)` (minimal in-house Borsh encoder for this single type, tested byte by byte against near-api-js; no `near-*` crate), strictly verified before being returned and before broadcast. **Hardened 2nd window**: Ethereum-style recipient (`0x…`).
- **Fees are not in the NEAR transaction**: they are charged at the block's gas price. Kyro displays an estimate and an **upper bound** (2 × gas × max(current price, protocol minimum price)) computed from the protocol configuration read from the RPC, and refuses if amount + bound exceeds what is available. A lying RPC about the gas price therefore cannot make you pay more than what the protocol actually charges; it can only distort the displayed estimate.
- **The server (FastNEAR RPC) can lie about**: balance and storage reserve, **existence** of the recipient (a nonexistent named account announced as existing: transfer rejected by the network, amount refunded, fees lost; an implicit account announced as existing changes nothing), nonce and block (transaction rejected), history (FastNEAR API). It can change neither the signed recipient nor the signed amount.
- **Scams.** Implicit account = 64 hexadecimal characters: a typo creates an account that nobody controls (funds lost) — the screen says so, and lookalike address detection applies. Uppercase identifiers are refused (it would be a different account, or none). An exchange's EVM deposit address ≠ NEAR account `0x…` (hardened warning; nonexistent: refused).
- **Residual risks.** One account per number (`m/44'/397'/a'`, path of near-seed-phrase / near-cli; account 0 = `m/44'/397'/0'`). No named account as sender. Staking: through the Staking path only (see "Staking" below). Tokens: USDC (Circle) and USDt only (NEP-141 contracts known to wallet-core; the recipient's storage registration is paid when needed and shown); any other contract or method is refused. Not from a hardware account. Default servers only (no custom NEAR RPC yet). Hardware wallet: Ledger only, with a different path (see "Sui, Aptos, Algorand, NEAR, Cosmos Hub on Ledger").

### Sui (SUI)

- **Rust builds, decodes and refuses.** Kyro **builds the transfer itself**: SUI coins, reference gas price and epoch read from the server, BCS written by wallet-core (hand-written, strict subset, **identical re-encoding required**). Only one template is signable: `SplitCoins(GasCoin, [amount])` then `TransferObjects([coin], recipient)`, or `TransferObjects([GasCoin], recipient)` for "entire balance" — exactly what the official SDK produces (two mainnet transfers rebuilt byte for byte, digest and signature verified against the chain). Everything else is refused before the window: Move call (hence no approvals, no contracts), input object, another token, **sponsored** transaction (gas paid by someone else), gas paid from the address balance, `ValidDuring` expiration. ed25519 signature of BLAKE2b-256(intent `[0,0,0]` ‖ BCS), verified before being returned and again before sending (key = sender).
- **Native window**: signing account, recipient **in full** (a Sui address has **no checksum**: a typo yields another valid address), amount, token `SUI (0x2::sui::SUI)`, gas budget, gas price and reference price, simulated fees, gas coins **one by one** (object ID and version decoded from the signed bytes, balance re-read live; beyond 5, the count and total of the others), limit epoch, digest. **Hardened 2nd window**: "entire balance", sending to oneself, budget > 0.1 SUI. Short forms (`0x2`) and **SuiNS** names are refused (a name resolved by a server could point elsewhere).
- **Bounded replay.** Each transfer expires at the end of the next epoch (≈ 1 to 2 days): a signed transaction kept by a third party cannot be submitted months later, even if its gas coins have not moved. Without expiration: refused at signing.
- **The server (Sui Foundation's GraphQL) can lie about**: balances, the coin list, reference price, epoch and **simulation** (displayed fees, amount received for "entire balance"). It cannot change what is signed: recipient, amount and maximum budget are in the bytes built by Rust; a fake low price only makes the transaction fail, a price > 10 × the reference is refused, a simulation that moves other funds or does not credit the intended amount is refused. The budget is a **cap**: at worst, that cap is charged. The server is checked against the chain identifier (`chainIdentifier`) on every response.
- **Residual risks.** One address per account (`m/44'/784'/a'/0'/0'`, account 0 = that of Sui Wallet / Slush). Tokens: Circle's USDC only (coin type known to wallet-core, every coin re-read live, simulation must move exactly that token); other Sui tokens are neither displayed nor sendable. Not from a hardware account. Sui's "address balance" (accumulator, 2026) is displayed but not spent. No custom server. Hardware wallet: Ledger only. Public endpoint is rate-limited.

### Hedera (HBAR)

- **Key.** ECDSA secp256k1 `m/44'/3030'/0'/0/a`: the "standard" ECDSA path of the Hedera SDKs (`toStandardECDSAsecp256k1PrivateKey`), the one HashPack uses for an ECDSA account (official SDK vectors verified). Your "address" is the **EVM address** of that key: the first HBAR sent to it creates your `0.0.x` account (automatic creation, HIP-583). **ED25519** accounts (Ledger, older HashPack accounts, `m/44'/3030'/0'/0'/a'`) are **not** supported: the same phrase imported into Kyro does not find them.
- **Rust decodes and refuses.** Kyro **builds the `CryptoTransfer` itself** (protobuf written by hand for this single message, cross-checked byte by byte against Google's protobuf runtime; identical re-encoding required): **one debit from your account, one credit to the recipient, nothing else**. Refused: any other transaction type (`CryptoUpdate` key update — account takeover —, `CryptoApproveAllowance`, `CryptoDelete`, contract calls, `EthereumTransaction`…), HTS tokens, spending by allowance (`is_approval`), hooks, scheduled transaction, unknown fields, a payer other than your account, transfer to yourself, validity > 180 s. One signed copy **per node** (the node is in the signed body), same transaction ID: the network executes at most one; the native window lists the nodes. **Hardened 2nd window**: maximum fee > 2 HBAR, sanitized memo. Low-S signature over `keccak256(bodyBytes)`, verified by Rust before sending.
- **Memo.** Boxed in the native window, **after** the amount and the fees (or "NO MEMO" (AUCUN MÉMO) with the platforms warning); the memo you type is refused if it exceeds 100 bytes or contains a control, invisible or direction character. Memos in the history are sanitized before display.
- **The server (mirror node) can lie about**: your `0.0.x` ID (a transaction for an account that is not yours fails with `INVALID_SIGNATURE`, without fees: pre-check), your balance, the recipient's existence and its "signature required" flag (transfer rejected by the network, actual fees lost), the exchange rate (the fee **cap** is displayed before signing), history. An EVM address is signed **as is** (alias): it is the network, not the mirror node, that chooses the credited account. gRPC-web proxies see the signed transaction and may not forward it (nothing is then executed).
- **Scams.** **Forgotten memo** to an exchange: boxed ("NO MEMO" (AUCUN MÉMO)). **EVM address of an account found by its public key**: if your account was created with your key but without an alias, receiving on the EVM address would create ANOTHER account; Receive then shows only `0.0.x`. HIP-15 checksums (`0.0.123-vfmkw`) verified for the right network.
- **Residual risks.** One address / one account per Kyro account number. Tokens: USDC only (HTS token known to wallet-core; association with TokenAssociate shown in the native window, ≈ $0.05); any other token, NFT or mixed transfer is refused. No staking. Hardware (Ledger ED25519) accounts: HBAR only. No real send from a funded account has been made yet (see docs/ARCHITECTURE.md).

### Polkadot (DOT on Polkadot Asset Hub)

- **Keys.** sr25519 derived from the phrase's **entropy** (`substrate-bip39`, `schnorrkel`: Substrate's crates), like Polkadot.js, Nova, Talisman and SubWallet: account 0 = the phrase's root key, account `a` = `//a`. The sr25519 root is kept during the unlocked session (for addresses), like the Cardano root; signing re-derives the key from the vault with the password. **Not Ledger-compatible** (ed25519 `m/44'/354'/…`): the same phrase gives different addresses.
- **Rust decodes and refuses.** Kyro **builds the transfer itself**; only one call is signed: `Balances.transfer_keep_alive` (which cannot empty your account below the existential deposit) to an account (`MultiAddress::Id`). Its index (`0x0a03`) is **pinned in Kyro** and must be confirmed by the runtime metadata (name, arguments, types), like every **transaction extension**: an unknown extension or one of unexpected shape stops everything ("Kyro must be updated"). Refused: any other call (`utility.batch`, `proxy`, `staking`…), tip, fees in another asset, `CheckMetadataHash` enabled, **immortal** transaction (a signed transaction without an era would stay valid indefinitely) or one valid for more than 4096 blocks, another genesis, another runtime version, extra bytes, non-canonical encoding (identical re-encoding required, at signing as at broadcast). sr25519 signature verified before broadcast. No 2nd window: nothing unusual is accepted.
- **The node (Parity) can lie about**: balances, locked portion, **existence** of the recipient account (Kyro may then refuse a valid send, or accept one below the existential deposit that the chain will reject: fees lost), existential deposit, nonce, estimated fees (displayed "≈", the chain charges its real fees), inclusion status. It **cannot** change what is signed: the call and encoding are Kyro's; genesis, runtime versions and the era's block are part of the signature, so lying metadata only produces an invalid transaction. Verified live on mainnet: the runtime accepts Kyro's signature (`validate_transaction` answers "Payment" — account without funds — and not "BadProof").
- **Scams.** Address from another Substrate network (Kusama, generic format "5…" on mainnet): refused (SS58 prefix), even if it is the same key. Address poisoning: same check as the other chains, but **without server history** (only your address book, your accounts and your sends from this Kyro serve as reference).
- **Residual risks.** **History via Statescan** (public API without key, undocumented, mainnet only): it learns your Polkadot address (via Tor); if it is unreachable or answers in an unexpected format, the UI says "history unavailable" and only sends made from this device appear; Kyro does not verify these transfers on a node (display only, the balance comes from Parity's node). Tracking says "finalized" when the **nonce** is consumed in the finalized state; Kyro does not read events, so a transfer that was included but failed (balance changed between verification and inclusion) would also be "finalized": check the balance. Tokens: USD₮ (asset 1984) and USDC (asset 1337) on Asset Hub only, their metadata re-read and compared with wallet-core's table before any use, fees in DOT; no token history. No custom server or hardware wallet for Polkadot. A single default node (Parity): if it goes down, error, no fallback.

### Algorand (ALGO)

- **Rust decodes and refuses.** Kyro **builds the payment itself** (fees, validity window and genesis read from algod, canonical msgpack written by wallet-core); strict decoding with **byte-for-byte** identical re-encoding: **only `pay` payments** from our account, on the app's network (genesis id **and** hash compiled into wallet-core, also required from the server) — never `axfer`, `appl`, `keyreg`, `acfg`…; **`close` (close-remainder-to: empties the whole account to another address) and `rekey` (gives control of the account to another key) are refused**, as are grouped transactions (`grp`, where another transaction in the group could cost you), the lease (`lx`) and any unknown field; validity window ≤ 1000 rounds (Kyro: 200, ≈ 9 min), so a signed transaction never stays valid for long. **Hardened 2nd window**: note (sanitized text, or hexadecimal if binary), fees > 0.01 ALGO. The native window shows what Rust decoded: recipient, amount, note, fees, network (genesis), validity rounds, ID. `ed25519-dalek` signature (`verify_strict`), re-verified before broadcast; the ID returned by algod must be ours.
- **Keys.** Path `m/44'/283'/a'/0/0` derived like Ledger's Algorand app (Ledger OS BIP32-Ed25519, `ed25519-bip32` crate for the children, RustCrypto HMAC for the root; verified against the Ledger app's test vector). **Not compatible with Pera's 25-word phrases** (a raw key without BIP39): they cannot be imported, and a Kyro phrase does not open in Pera.
- **The server (AlgoNode) can lie about**: balance, **minimum balance** (yours and the recipient's), existence of the recipient account, rekey of your account, last round and fees (transaction rejected, or fees displayed higher — capped by the 2nd window beyond 0.01 ALGO), history. It cannot switch networks without being refused (genesis verified).
- **Residual risks.** One address per account. No custom Algorand server (AlgoNode sees your addresses, not your IP in Tor mode). Tokens: USDC and USDT (ASA known to wallet-core) only, after an opt-in signed by you (raises the minimum balance by 0.1 ALGO); close-out and clawback are refused. Hardware wallet: Ledger only (ALGO only, no tokens yet).

### TON (Toncoin)

- **Rust decodes and refuses.** Kyro **builds the transfer itself** (seqno and states read from TON Center, wallet-core cells, standard **v4R2** wallet, official code verified by its hash); strict decoding with **byte-for-byte** re-encoding: **a single message**, simple send (op 0: never installing or removing a **plugin**, which would give a contract the right to drain your wallet), mode 3 (amount + fees) or 130 (entire balance), internal message without other currencies, without `StateInit` (no contract deployment), empty body or **text comment** only (never a contract call, hence no jettons or NFTs); our `StateInit` only on the very first send (seqno 0). Recipient on the masterchain, raw address `0:…` (without checksum), address flagged testnet on mainnet: refused. **Hardened 2nd window**: comment with invisible or control characters (displayed sanitized). ed25519 signature (`ed25519-dalek`) verified.
- **Testnet cannot drain mainnet.** A v4R2 signature does **not** contain the network: with the standard wallet id, a transfer signed on testnet would be valid on mainnet for the same key at the same seqno (same recipient, same amount) — a "send me 100 test TON" would suffice. Kyro therefore uses a **different wallet id on testnet** (`0x4B59524F`): a different test address, and no test signature is valid on mainnet. Each message is valid for only **10 minutes** (`valid_until`), and Rust refuses to sign or broadcast beyond that.
- **The server (TON Center) can lie about**: balance, **seqno** and the state of your wallet (transfer rejected by the network, nothing is sent), **recipient state** — a lying server can make an active contract look "not yet active": Kyro then sends **without bounce** (if the contract fails, the funds stay there); estimated fees (displayed "≈", the network charges them); received history and comments.
- **Scams.** **Forgotten comment** to an exchange: boxed in the native window (or "NO COMMENT" (AUCUN COMMENTAIRE)), field always visible in Send. Fake tokens ("USDT" sent by anyone): Kyro only displays and sends Toncoin. Address poisoning: the **address poisoning alert** on the Send screen applies (an address is compared **per account**: `EQ…` and `UQ…` of the same account are the same); the native window shows both forms of the address.
- **Residual risks.** Same words as **Trust Wallet** (same address at account 0); **not** Tonkeeper / Tonhub (different phrase format) nor Ledger (different path). Tokens: USD₮ only (jetton master known to wallet-core, token wallet verified; from a Ledger: see "Tokens from a hardware account"); no staking. No real mainnet or testnet broadcast from Kyro at the time of writing (see docs/ARCHITECTURE.md): the signature is verified against transfers **actually broadcast on mainnet** by Trust Wallet (vectors, identical message hash).

### Cosmos Hub (ATOM)

- **Rust decodes and refuses.** Kyro **builds the transaction itself** (account number, sequence and height read from the server, simulated gas, wallet-core protobuf encoding); strict decoding with identical re-encoding at every level (SignDoc, TxBody, message, AuthInfo, key): **a single `MsgSend` of uatom** from our account, with our key, in SIGN_MODE_DIRECT, for the network's chain-id (`cosmoshub-4` or `provider`) — never **MsgGrant / MsgExec** (authz: giving a third party the right to spend in your place), **MsgDelegate** / redelegation, IBC **MsgTransfer**, MsgMultiSend, fees paid or authorized by a third party (`payer`, `granter`), multisig, Amino JSON, "unordered" transaction, extension options, IBC tokens; **`timeout_height` is mandatory** (≈ 10 min: without it, a signed transaction would stay valid until its sequence is used). The memo is **boxed** in the native window (or "NO MEMO" (AUCUN MÉMO) with the platforms warning), after the amount and the fees. **Hardened 2nd window**: fees > 0.1 ATOM, memo needing sanitizing (invisible or control characters, or more than 256 characters: displayed sanitized, the exact hexadecimal in the 2nd window). libsecp256k1 RFC 6979 **low-S** signature of SHA-256(SignDoc), verified; before broadcast, Rust re-verifies the signature over the rebuilt SignDoc with the account number read live. `k256` is not used (see advisory RUSTSEC-2026-0387 on `crypto-bigint` 0.5); protobuf goes through `prost`'s derive (hand-declared messages, used fields only), not through `cosmos-sdk-proto` (a much larger dependency tree, `tendermint-proto`).
- **The server (LCD) can lie about**: balance and available balance (vesting), history (and what the node indexes), **simulation result** (gas underestimated: transaction rejected "out of gas", fees lost; overestimated: capped at 500,000 gas), **gas price** (capped at 1 uatom/gas: at worst ≈ 0.84 ATOM of fees, amount **displayed** and hardened beyond 0.1 ATOM), sequence and account number (transaction rejected, never diverted: the account number and chain-id are signed), height (limit block displayed in minutes).
- **Scams.** **Forgotten memo** for an exchange: field always visible, memo boxed in the native window. **authz / feegrant** ("sign to claim your airdrop" that actually grants the right to drain the account): impossible to sign. Address from another Cosmos chain (`osmo1…`, same key, different prefix) or a validator address (`cosmosvaloper1…`): refused with a message that says so. Address poisoning: the **address poisoning alert** on the Send screen applies (`cosmos1` prefix + first character, lowercase bech32).
- **Residual risks.** One address per account (`m/44'/118'/a'/0/0`, account 0 = `m/44'/118'/0'/0/0`). No staking or IBC tokens. History limited to what the public node indexes (recent blocks). No custom server for now: the default LCDs see your addresses (without your IP in Tor mode).

### Aptos (APT)

- **Rust decodes and refuses.** Kyro **builds the transfer itself** (sequence, gas price, simulated gas, 10-minute expiration; BCS written by wallet-core); strict decoding with identical re-encoding: **only `0x1::aptos_account::transfer`** from our account, without type arguments — never a Move script, another function (hence no **key rotation**, no contract call), multisig, a transaction without a sequence number, a fee payer or a secondary signer. The `chain_id` must be that of the app's network, also verified with the node (`/v1`). At signing time, Rust re-reads the account (sequence, balance, authentication key unchanged) and **re-simulates** the transfer. **Hardened 2nd window**: sending to oneself, maximum fee > 0.02 APT. `ed25519-dalek` signature (`verify_strict`) over `SHA3-256("APTOS::RawTransaction") || BCS`; before broadcast, only one ed25519 key is accepted, the sender's.
- **The server (Aptos Labs) can lie about**: balance, history (indexer), sequence (transaction rejected), gas price (capped at 10,000 octas per unit) and **simulation** (maximum gas capped at 20,000 units: at worst ≈ 2 APT of maximum fees, **displayed**, and the 2nd window beyond 0.02 APT), existence of the recipient account (information only).
- **Scams.** Aptos addresses **have no checksum**: any 64 hexadecimal characters are a valid address; Kyro requires the full long form (no short `0x1…`, no ANS name), repeats it in full in the native window with "compare it in full", and the **address poisoning alert** applies (1-octa transfers from lookalikes: suspect by default). Approvals and contract calls (drainers): impossible to sign.
- **Residual risks.** One address per account (`m/44'/637'/a'/0'/0'`, Petra's path). An account whose key was changed elsewhere (rotation) can no longer be signed by Kyro (explicit refusal). Tokens: USDC (Circle) and USDt (Tether) only (fungible-asset metadata known to wallet-core), other fungible assets are refused; no custom server; hardware wallet: Ledger only. Aptos Labs rate limit without a key: over Tor, a shared exit relay may be temporarily limited (error displayed, nothing in the clear).

### Cardano (ADA, native tokens)

- **Rust decodes and refuses.** Kyro **builds the transaction itself** (UTxOs and parameters read from Koios, wallet-core encoding); strict CBOR decoding with identical re-encoding: **only payments** (inputs, ADA + token outputs, fees, ttl, CIP-20 message) — never a certificate or a rewards withdrawal in a payment (they only go through the Staking path, further below, and only for your own key), never a mint, Plutus script, datum, collateral, required signer, vote or governance proposal; an output below its min-UTxO, metadata other than a CIP-20 message, and unknown fields are refused. At signing time, Rust **re-reads our UTxOs**: each input must be one of our unspent UTxOs and inputs = outputs + fees (ADA and each token). Byron, script (funds stuck without a datum), pointer, staking and other-network recipients are refused. **Hardened 2nd window**: CIP-20 message (sanitized lines), token outside the verified table, token name needing sanitizing (shown in hexadecimal only), fees > 5 ADA, no ttl. The min-UTxO is computed with checked arithmetic (an absurd `coinsPerUTxOByte` gives an impossible minimum, hence a refusal, never a tiny "wrapped-around" minimum). `ed25519-dalek` signature verified, key cross-checked with `ed25519-bip32`.
- **The server (Koios or your own) can lie about**: balance, tokens, history, UTxOs (fake UTxOs: transaction rejected by the node; hidden UTxOs: lower balance displayed); **protocol parameters** (bounded by Kyro; an inflated `min_fee` within those bounds makes you pay more, amount **displayed**); current slot (ttl too short or too long, displayed in minutes).
- **Scams.** **Fake tokens** with the same name (anyone can create "USDM"): each token is shown with its **full policy id**, text name **and** hex, "verified" only for DJED, USDM, iUSD (mainnet); anything else → hardened. A certificate for **another** staking key, pool registration or retirement, DRep or committee certificates, governance votes and proposals: impossible to sign; delegation of **your** key goes through the Staking path (further below). Address poisoning: the **address poisoning alert** on the Send screen applies (see "What Kyro protects").
- **Residual risks.** **Single-address mode** (per account): receiving and change on the same base address, which contains your staking key — your entire Cardano history is linked. The CBOR is a hand-written subset (not `minicbor`, license not on the list), tested against Trezor vectors and real preprod transactions, but young. **One real preprod broadcast** (send to oneself, minimum fee) from the public address of the CIP-19 vectors, whose payment key comes from the published test phrase (the preprod faucet, for its part, has a captcha). "Send all" leaves about 1 ADA: Kyro always keeps a change output.

### Kaspa (KAS)

- **Keys and addresses.** BIP39 + BIP32 secp256k1, `m/44'/111111'/a'/0/i` (receive) and `…/1/i` (change), **same path on testnet-10** (prefix `kaspatest:`), like Kaspa NG, Kaspium and the rusty-kaspa wallet ("gen1"): official rusty-kaspa v2.1.0 vectors replayed (20 receive addresses + 20 change addresses from a master key, the `kpub` of a 24-word phrase, one `kaspatest:` address). Kyro shows `…/0/0`, returns change to `…/1/0`, and reads balance, coins and history from the **first 20 addresses of each chain** (a phrase coming from Kaspa NG / Kaspium shows its funds). **Schnorr** P2PK addresses (BIP340, x-only key). The old KDX / web derivation (`m/44'/972/…`) is not read.
- **Rust builds, decodes and refuses.** Kyro **builds the transaction itself** (coins read from the API, selection by descending amount, mass and fees computed by wallet-core, change to **your** `…/1/0` address); a transaction built by the server is never signed. Strict decoding: **version 0 only** (Toccata's v1 format — compute budgets, covenants, subnetworks — is neither produced nor signed), native subnetwork, gas 0, no payload, lock time 0, sequence 0, one sig-op per input, 1 or 2 outputs, no null output, script version 0, inputs = **P2PK coins of this account** (otherwise refused), no duplicate input, outputs ≤ inputs, mass ≤ 100,000 g, fees ≥ relay minimum. At signing time, Rust **re-reads the coins live**: each input must still be an unspent coin of this account, and the amount and script come from that re-read, never from the interface. Signature: Kaspa signature hash (keyed BLAKE2b `TransactionSigningHash`, `SIG_HASH_ALL` only) checked against rusty-kaspa's **official vectors**, BIP340 Schnorr from libsecp256k1 with auxiliary randomness, **each signature re-verified**; at broadcast, each signature is re-verified against the re-read coins and the identifier returned by the server must be ours. **Hardened 2nd window**: output to an unknown script, fees > 1 KAS or > 10 × the relay minimum.
- **Mass and fees (KIP-9).** Compute mass (bytes + 10 × script bytes + 1,000 per sig-op), transient mass (4 × bytes, normalized ÷ 2) and KIP-9 **storage mass** (`C · (Σ 1/outputs − Σ 1/inputs)`, C = 10¹²); fees = 100 sompi per gram of relay mass (mempool rule since Toccata, like the official wallet), or, if the network is busy (server estimate above the minimum, capped at 100 ×), estimate × total mass. A recipient under **0.2 KAS** is refused (its storage mass alone would approach the limit); change that would exceed the mass limit is **never created**: it is added to the fees if ≤ 0.2 KAS ("No change…" in the native window), otherwise more coins are taken.
- **The server (api.kaspa.org / api-tn10.kaspa.org) can lie about**: balance, coins (an invented coin or one with a wrong amount makes the signature invalid — the signature hash commits to the amount and script of each spent coin — so the transaction is rejected by the network; a hidden coin only lowers the displayed balance), history (a transaction that touches none of your addresses is discarded; a counterparty that is not a valid address is not displayed), fee estimate (capped, fees shown before signing), acceptance. It **cannot** make you sign a different output, a different amount or different fees than those in the native window, nor pass itself off as another network (`networkName` checked on every read). Each announced coin must pay exactly the script of your address, otherwise the whole list is refused.
- **Scams.** Address poisoning: the **address poisoning alert** on the Send screen applies (comparison after `kaspa:q` / `kaspatest:q`). Address from another network (`kaspatest:` on mainnet and vice versa): refused with the reason.
- **Residual risks.** **No real broadcast** by Kyro, neither on testnet-10 nor on mainnet (no test KAS in the public test wallets; the testnet-10 faucet was not used): the chain construction → signing → `POST /transactions` is tested on official vectors, on a **real mainnet transaction** (identifier, mass and two signatures recomputed and verified) and on API responses, not against the node. A single operator (the Kaspa developers' public API), no custom server for now. The 40 addresses read are sent together to the server (like an Electrum wallet): it can link them. Hardware wallets: not offered.

### Monero (XMR)

- **Keys.** `k = BIP32-secp256k1(seed, m/44'/128'/a'/0/0)`, spend key `sc_reduce32(keccak256(k))`, view key `sc_reduce32(keccak256(spend))`: the scheme of Ledger's Monero app, **not** a native Monero phrase. The 25-word Monero phrase for this key (Settings, **protected phrase window only**) restores the same wallet in Monero GUI, Feather or Cake Wallet; a 25-word Monero phrase created elsewhere cannot be imported into Kyro. Kyro's testnet = **stagenet**.
- **No home-grown crypto.** Addresses, subaddresses, output scanning (view tags, amount decryption, commitment verification), key images, CLSAG, Bulletproofs+, decoy selection and construction: **monero-oxide / monero-wallet 0.2** (Cypher Stack audit, May 2025). Kyro only adds the BIP39 → Monero mapping above, the 25-word encoding (word list + CRC32) and the encryption of the scan state (RustCrypto's XChaCha20-Poly1305).
- **What the node sees.** Kyro talks to a `monerod` node (by default: Cake Wallet's public node, stagenet: Stack Wallet's) and **scans blocks locally**: neither the view key nor your addresses are sent to it. No "light wallet" server (MyMonero, `monero-lws`) is used, precisely because it requires the view key, and so sees all your incoming payments. The node does see: the block ranges you download (so roughly since when your wallet has existed), the decoy outputs requested for a send (the real one is hidden among 16, but a malicious node can try to skew the decoy distribution; monero-wallet checks what it can, not everything), your transactions **at the moment you publish them**, with the IP of a Tor exit relay (or yours in clear mode, which links your IP to your transaction). To reduce this risk: your own node, ideally as a `.onion`.
- **Rust decodes and refuses.** Recipient: standard address, subaddress or integrated address of the right network; "featured" addresses, another network and non-canonical encodings refused. The transfer is built **by Rust** (inputs, decoys, fees capped at 4,000,000 piconero/weight, change to the primary address), held in Rust (single use, 10 min), then signed after the password and the native window; after signing, Rust verifies that the transaction creates **exactly** the intended outputs (`Eventuality`), that the fees are those displayed and that it spends exactly the intended outputs. **Hardened 2nd window**: integrated address (payment ID), fees > 0.01 XMR, fees > amount, send to one of your own addresses.
- **Residual risks.** The scan state (your outputs, their key images, the history) is stored on disk, encrypted with a key derived from the view key: anyone who obtains your seed reads it, like everything else. The session seed is also used to compute key images during the scan (see "Known shell limitations"). A lying node can hide incoming payments or delay your synchronization (not steal funds). Monero on a hardware wallet: not supported. This integration's code is young: tested against official vectors (phrases, addresses) and a simulated chain, **never broadcast on stagenet** from this repository.

### Known shell limitations (internal review of 2026-10-31)

- **Seed in memory during the session.** Signatures re-decrypt the vault with the password, but the session keeps the seed to derive public addresses (Solana, TRON, XRP, Stellar, Cardano, NEAR, Sui, Aptos use fully hardened paths: impossible from a public key). Replacing it with precomputed public data would require asking for the password again for each new account: not done.
- **No lock *before* sleep** (see "Auto-lock"): only on wake.
- **Native windows and screenshots**: capture protection covers the main window (setting) and the phrase window (always), **not** the system confirmation dialogs; it does nothing on Linux, and macOS 15+ capture tools may bypass it.
- **No native window has been clicked by a human yet** (see the warning at the top): their texts are tested, not their rendering on every system (maximum length, font).

## Multiple accounts per chain

Details: [docs/IPC.md §2.9](docs/IPC.md). All accounts come from **your** recovery phrase (standard paths: see the IPC table); an account is just a public bookmark (number + name) in `settings.json`, unencrypted like the rest of that file: anyone who reads the app folder sees how many accounts you use and their names (not their keys). **Account 0** of each chain is exactly the one from before (tested). What protects:

- **Rust chooses the key, not the interface**: each signing command receives an account number, and the **native window** states on its first line which account and which path sign; a number absent from your list (compromised interface, or bug) is displayed as "unknown" and requires a **hardened 2nd window**. The account name is displayed between "…" and cannot contain control characters, or invisible or direction-changing characters (refused on save, stripped on display).
- **Bitcoin, Litecoin, Dogecoin, Bitcoin Cash, Dash**: Rust signs only the inputs of the chosen account; an input from another of your accounts is treated as foreign (not signed, 2nd window), and change is recognized only in that account.
- **Limits**: the accounts of one vault are linked by the same phrase (and, on the server side, by the requests made from the same app — Tor isolates circuits per chain, not per account). Compact filters: only account 0 is watched. Bitcoin Core: an account added after setup requires restarting it. **No real broadcast from an account no. 2 or higher** has been made yet.

## Simulation before signing (EVM)

Before the password on a swap or an Earn call, Kyro asks your RPC node what the call would do and shows it in plain words, with warnings for a call that would fail, an unlimited approval, a contract unknown to Kyro or deployed in the last 7 days, and a token outside its list. The node is the only party asked. **Limits**: the node is trusted for this result and can lie; a contract can behave differently at signing time, or for a simulator; public nodes often offer no trace, in which case Kyro says it cannot see the moves, and pruned nodes give no contract age. A clean simulation is not a proof of safety: the decoded review and the native window decide. The node also sees the call before you sign, even if you then cancel.

## Several wallets

Details: [docs/IPC.md §2.9b](docs/IPC.md). Each added wallet is a separate vault file in the same format, with its own password and its own attempt counter; the first vault file is never rewritten, so no migration exists to go wrong. Only one wallet is open at a time: switching ends the session and asks for the password, so a single seed at most is in memory. An unlock started before a switch is refused, and switching does not clear the delay after wrong passwords. **Limits**: wallet names, and the fact that several wallets exist, are plain text on disk and shown on the lock screen. Removing a wallet takes it off the list but leaves its encrypted file on the disk (`.kyrovault.removed`): a weak password stays attackable until you delete that file yourself. Settings, servers, contacts, hardware-wallet accounts and watch addresses are shared by all wallets, and the same servers see the requests of each wallet you open (Tor hides your IP, not that one app asked). Compact filters (`cbf`, off by default) keep one state per network: use them with the first wallet only.

## Watch addresses

A watch address is a public address or xpub followed with no key. Kyro stores it in plain text next to the vault, like hardware-wallet accounts: anyone who reads your disk sees which addresses you follow. Rust refuses private keys and recovery phrases when adding one and when loading the file. Nothing can be signed: Send, Swap and Earn stop on a clear screen, and every build, sign and broadcast method of its adapters refuses. **Limits**: reading an xpub asks servers about each derived address, so a server can link them, as with your own accounts (Tor hides your IP, not that link). A Watch address proves nothing about ownership. Monero cannot be watched: a balance needs a private view key.

## Staking (Solana, Cardano, TRON, NEAR, Sui)

Technical details: [docs/IPC.md §2.8](docs/IPC.md). As with payments, **Kyro builds each operation itself**, Rust **decodes** it (wallet-core) and **re-reads the account state live** before the **native window**; a closed list of operations is accepted, always with **your** key as the only authority, and everything else is **refused** (not merely flagged). No hardware wallet for staking. **None of these operations entrusts your funds to anyone**: the validator, pool or SPO can neither spend nor lock them.

**No staking** for Bitcoin, Litecoin, Dogecoin, Zcash, XRP Ledger and Stellar: these protocols have none. **Cosmos Hub: not offered** (the protocol has it, Kyro refuses to sign `MsgDelegate`). **Ethereum (and EVM):** native staking (32 ETH and a validator that is always online) is not offered. Since 1.0.5 the Earn page offers ETH liquid staking with Lido and lending on Aave v3, through pinned contracts that Kyro decodes and shows before signing. These carry contract, governance and de-peg risk.

### Solana (Stake program)

- **What Kyro signs.** Only four operations: create a staking account derived from your address (`CreateAccountWithSeed`, seed `kyro-stake-N`, 200 bytes) + `Initialize` (staker = withdrawer = you, **no lockup**) + `DelegateStake`; delegate an inactive account; `Deactivate`; `Withdraw` **to your address**. The message must be exactly one of these (payer and sole signer: you).
- **Refused**: authority change (`Authorize*`: the takeover of a staking account), lockup (`SetLockup*`, or `Initialize` with a lockup or a custodian), `Split`, `Merge`, `Redelegate`, `MoveStake`, `MoveLamports` and any other Stake instruction; an authority or a withdrawal recipient that is not you; a sysvar in the wrong place; a staking account created without being initialized in the same transaction (anyone could initialize it in their own name); a wrong derived address. Tested on the 25 staking transactions in the Trezor firmware fixtures (Kyro's serialization reproduces Trezor's signatures byte for byte there) and on modified messages.
- **Hardened 2nd window**: **delinquent** validator (it no longer votes, no rewards), commission > 10%.
- **Risks.** The choice of validator (commission up to 100%, downtime) only costs **rewards**. **No slashing** in the Solana protocol as of 2026-10-30 (proposals exist, none is activated): the stake is not confiscated. Activation at the start of the next epoch and **cooldown of at least one epoch** (≈ 2 days; longer if a lot of stake moves at the same time: 9% of total stake per epoch), with no rewards during cooldown; a stake deactivated in the very epoch of its delegation is withdrawn immediately. The rent reserve (≈ 0.002 SOL) is returned on full withdrawal. `kyro-stake-N` accounts are publicly linked to your address.
- **The server (RPC) can lie about**: the list of validators, their commission, their status, their name (in any case **declared by the validator itself**, unverified) and the state of your staking accounts (activation computed by Kyro from the StakeHistory sysvar that the RPC provides). Consequence: a misleading display or a transaction rejected by the network, never a changed authority or funds sent elsewhere (the message itself is decoded by Rust).

### Cardano (delegation, Conway)

- **What Kyro signs.** For **your** staking key `m/1852'/1815'/0'/2/0` only: registration (certificate 7, deposit = the protocol's `keyDeposit`, **2 ADA**, refunded on deregistration), delegation to a pool (2), vote delegation (9: "always abstain", "always no confidence" or a `drep1…` DRep), withdrawal of **all** rewards to your reward account, deregistration (8, deposit refunded). The only output is the change to your address — a rule checked **in wallet-core** (a single output, to one of our addresses), no longer only by the shell; two witnesses: your payment key and your staking key.
- **Refused**: a certificate or a withdrawal for **another key** (or a script), pool registration / retirement, DRep certificates, committee certificates, MIR, combined or legacy-format certificates, governance votes and proposals, a deposit different from the protocol's, a refund different from the deposit paid, partial withdrawal, metadata, any output to another address. Tested on the Trezor fixtures (transaction hash **and signatures of both witnesses** identical) and on modified transactions.
- **Hardened 2nd window**: pool that has announced its retirement, margin > 10%, saturated pool (> 100%), inactive DRep. Retired or unknown pool, unregistered DRep: refused.
- **Risks.** Your ADA **stay on your address and remain spendable**: no lockup, **no slashing** on Cardano. The choice of pool (margin, fixed cost, saturation, a pool that does not produce blocks) only costs rewards. Timeline: the delegation counts at epoch N+2, first rewards paid at the start of N+4 (≈ 15 to 20 days, 5-day epochs). Since the Plomin upgrade, **withdrawing rewards requires a vote delegation**: Kyro checks this and proposes "always abstain". Delegating your vote to a DRep entrusts it with your governance **voting weight**, not your funds. The delegation is public and links all addresses of this staking key.
- **The server (Koios) can lie about**: the pools (**operator-declared** metadata, margin, saturation), the state of your key, the amount of rewards and the `keyDeposit` (capped by Kyro). Consequence: a misleading display or a transaction **rejected by the node** (the ledger itself checks the deposit, the refund and the exact withdrawal amount), never a delegation of another key.

### TRON (Stake 2.0 and votes)

- **What Kyro signs.** With your address as owner: stake (`FreezeBalanceV2`, BANDWIDTH or ENERGY, ≥ 1 TRX), unfreeze (`UnfreezeBalanceV2`), withdraw matured unfreezes (`WithdrawExpireUnfreeze`), cancel pending unfreezes (`CancelAllUnfreezeV2`), vote (`VoteWitness`, 1 to 30 SRs, **replaces all your votes**), claim vote rewards (`WithdrawBalance`). No memo, no `fee_limit`.
- **Refused**: **lending your resources to another account** (`DelegateResource` / `UnDelegateResource`), `TRON_POWER` resource, obsolete `support` field, a duplicate SR or one that is not a candidate, more votes than your TRON Power, and as everywhere: another owner, `Permission_id`, permission changes. Tested on the Trezor fixtures (identical signatures) and, on Nile, compared with java-tron's own encoding.
- **Hardened 2nd window**: SR ranked beyond the top 127 (its voters receive nothing), SR that keeps 100% of the rewards, unfreeze that will **reduce your votes** (the network reduces them proportionally: observed on Nile, 10 votes → 5 after unfreezing 5 TRX out of 10).
- **Risks.** Staked TRX are never confiscated (**no slashing** on TRON), but an unfreeze only returns the TRX after the **network delay** (`getUnfreezeDelayDays`: **14 days on mainnet**, 1 day on Nile, read live), then a withdrawal; during this delay they give neither resource nor vote. At most 32 pending unfreezes. Vote rewards can be claimed once per 24 h. The chosen SR (share kept, rank) only costs rewards.
- **The server (TronGrid) can lie about**: the list of SRs, their URL (the only "name", **declared**), their share, your resources and your rewards. Consequence: a misleading display or a transaction rejected by the network, never a vote or an unfreeze other than the one displayed (the `raw_data` is decoded by Rust).

### NEAR (staking pools)

- **What Kyro signs.** One `FunctionCall` from your implicit account to a staking pool: `deposit_and_stake` (the amount attached), `unstake` (`{"amount"}`), `unstake_all`, `withdraw_all`; 125 Tgas, nothing attached to the last three. Only pools created by the official factories (`*.poolv1.near`, `*.pool.near`; testnet `*.pool.f863973.m0`), and only if the pool's **live code hash** is the one its factory deploys (pinned in wallet-core; a pool running other code is refused).
- **Refused**: any other method (`deposit`, `stake`, `withdraw`, `ping`…), any other contract, several actions, extra arguments. The payment path still refuses every pool call.
- **Risks.** No slashing for delegators on NEAR. The pool keeps a share of the rewards (shown before signing; reinforced window above 20 %, or when the pool is not in the current validator set). Unstaked NEAR earn nothing and stay locked for **4 epochs** (≈ 1 to 2 days at the current block time) before `withdraw_all`. Rewards are added to the stake by the pool.
- **The servers can lie about**: your list of pools (FastNEAR), the pool's balances, fee and code hash, the validator set and the yield estimate. Consequence: a wrong display or a refused transaction; the call itself is decoded by Rust and cannot send NEAR anywhere but the pool you chose.

**Common limitation.** As with sends: real broadcasts made **without an interface** (see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)); no staking native window has been clicked by a human.

## Hardware wallets (Ledger, Trezor)

Technical details: [docs/IPC.md §2.3](docs/IPC.md). **Status: run by the project owner on real Ledger and Trezor devices. On a Ledger Nano X (`docs/LEDGER_CHECK.md`): addresses on Bitcoin, Ethereum, Solana, Litecoin, XRP, NEAR and TON and test signatures on Bitcoin, Ethereum and Solana, nothing broadcast. The rest is** tested on APDU exchanges recorded by Ledger and a simulated Trezor firmware (Trezor Safe 7: against Trezor's device-side THP implementation, see below). Supported chains (the same list as the app and README.md):

| Device | Chains |
|---|---|
| **Ledger and Trezor** | EVM chains, Bitcoin, Solana, Litecoin, Dogecoin, Bitcoin Cash, Dash, Stellar, Cardano (Trezor: Model T / Safe, not the Trezor One). Litecoin, Dogecoin, Bitcoin Cash and Dash on Ledger: main network only |
| **Ledger only** | XRP (Trezor does not give the XRP public key before signing), TRON (no Trezor app), Sui, Aptos, Algorand, Cosmos Hub, TON and NEAR (on TON and NEAR, a **different account** from the vault's for the same phrase: Ledger's path), Hedera (a separate **ED25519** account, which must first be created elsewhere — Ledger Live, HashPack… — with this Ledger). No Trezor app exists for these chains |
| **Trezor only** | Zcash (transparent addresses) |
| **None** | Monero, Polkadot, Kaspa (reasons below) |

**Tokens from a hardware account**: EVM tokens (ERC-20), **Solana SPL tokens** (Ledger and Trezor; the recipient's associated token account is created when missing), **TRON TRC-20** (Ledger), **TON jettons** (Ledger) and **Stellar assets** (Ledger and Trezor, trustline included) are supported, through the same build, Rust decoding and native window as the vault. Solana: the Ledger Solana app clear-signs the token transfer; if it cannot show an instruction it refuses until you "Enable Blind signing in the Solana app settings" (Kyro says so). A Trezor receives the destination token account with its wallet (`SolanaTxTokenAccountInfo`, only when Rust has checked it is that wallet's associated token account), so it shows the recipient wallet. TRON: the Ledger Tron app clear-signs USDT and the tokens in its list; otherwise it asks for "Allow data" / "Custom contracts" in the Tron app settings (Kyro names the setting). TON: USD₮ only, on the TON app ≥ 2.2.0 (older apps are refused before signing): Kyro sends the app its known-jetton hint, the app rebuilds the transfer body, recomputes your jetton wallet from its own key and table, requires both to match what it signs, and shows "Jetton amount" in USDT and the recipient, with no blind signing. A comment on a jetton transfer is refused on Ledger (the app would show at most a hash). Stellar: Circle's USDC, the payment and its trustline (ChangeTrust): the Ledger Stellar app decodes the whole transaction (asset code, issuer, amount, destination, limit) and a Trezor rebuilds the XDR from the fields it receives, shows them, and its signature only verifies if they are what the envelope says; no hash signing. On the other chains (Sui, Aptos, NEAR, Algorand, Polkadot Asset Hub, Hedera, Cardano native tokens) **token sends from a hardware account are refused for now** — native coins only. Use the Kyro vault for those tokens.

### What the device protects

- **Private keys** never leave the device; malware on the computer cannot read them.
- **The final confirmation** is done on the device's screen, which the computer does not control. Malware can alter what Kyro displays, but not what the device displays nor what it signs without your physical approval — **provided that the device can decode the transaction** (see blind signing).
- The PIN (and the passphrase on Trezor T / Safe) is entered **on the device**.

### What Kyro still shows and verifies

| Step | Measure |
|---|---|
| Before signing | Rust decodes the transaction and displays it in the **native system window** (recipient, amount, token, fees, change, memo); anything unknown (undecoded BTC output, contract call, unknown Solana instruction) or that the device will not be able to display (**blind signing**) requires a **hardened 2nd confirmation**. |
| Right device? | Before any signature or address display, Kyro re-reads the device's keys and compares them with the registered account (`HW_WRONG_DEVICE`). |
| Receive address | `hw_verify_address` displays the address **on the device** and compares it with the one Kyro derives itself from the registered xpub; any difference is a blocking error (`HW_ADDRESS_MISMATCH`). Verify it on the device's screen before sharing it. |
| After signing | Each signature is verified by libsecp256k1 / ed25519-dalek against the expected key and the sighash (BIP143/BIP341) or hash (EIP-1559) recomputed by Rust; recovered EVM address = expected address, low-S required; Solana in strict verification. A wrong, missing or other-input signature is refused (`HW_BAD_RESPONSE`). |
| Transport | One lock per device, bounded timeouts, cancellation and unplugging handled: the operation is cleanly abandoned, never an infinite wait, nothing is returned half-done. |

### What remains at risk

- **Blind signing.** When the device cannot decode (contract call, ERC-20 without a descriptor on Ledger, some Solana instructions), its screen shows only a fingerprint or raw data: only Kyro's summary describes the transaction, and a compromised computer can falsify that summary. The hardware wallet then protects only the keys, not your consent. Kyro flags this with a hardened confirmation; keep blind signing **disabled** in the Ledger apps until you need it.
- **Ledger ERC-20 descriptors ("CAL").** For a Ledger to display a token in clear, Ledger signs a descriptor (symbol, contract, decimals, chain). Kyro does **not** call Ledger's service: it embeds a few descriptors (mainnet USDC and USDT, Sepolia tUSDC) downloaded once and **verified offline** against the public key published by Ledger (in the tests and before each use). This is trust delegated to Ledger: a descriptor signed by mistake by Ledger would be displayed as authentic. Adding tokens would require either embedding them in every version, or querying `crypto-assets-service.api.ledger.com` (a new host, via the allowlist and Tor) — not done.
- **Device supply chain.** A counterfeit, intercepted or firmware-tampered device can display one thing and sign another, or generate predictable keys. Buy it directly from the manufacturer, verify its authenticity (Ledger: "Genuine" check; Trezor: authenticity check in Trezor Suite), keep the firmware up to date, and initialize it only with a phrase generated by the device itself. Kyro cannot detect a malicious device that correctly signs the transaction displayed by Kyro.
- **xpubs in clear on disk.** `hw-accounts-<network>.json`, next to the vault, contains xpubs in **unencrypted JSON**: anyone who reads this file knows all your past and future addresses and your history (privacy, not funds). Someone who can **write** it could put their own xpubs in it: Kyro would then display fake receive addresses as long as the device is not plugged in. Hence the rule: **always verify a receive address on the device** (`hw_verify_address`), which detects the substitution; signing, for its part, always re-reads the device's keys first.
- **Trezor One: PIN grid.** The Trezor One has no PIN entry on the device: it displays a shuffled 3 × 3 grid, and you click the corresponding **positions** in Kyro. Kyro only receives positions, useless without the device's screen; malware that sees the device's screen (camera) and your clicks could reconstruct the PIN. A passphrase to be typed on the computer (Trezor One) is **refused**.
- **Litecoin, Dogecoin, Bitcoin Cash, Dash, XRP, TRON, Stellar: youngest code.** Written from Ledger's host libraries (`hw-app-btc` for the legacy Bitcoin protocol of the Litecoin / Dogecoin / Bitcoin Cash / Dash apps, `hw-app-xrp`, `hw-app-str`, `hw-app-trx`) and Trezor's protobuf messages, tested only against simulated responses (APDU encoding, exchange order, response parsing): **no real exchange recorded** for these apps, unlike Bitcoin. What does not depend on the device is verified: each signature is checked by wallet-core (BIP143 / legacy / FORKID sighash recomputed and key derived from the xpub; Kyro's XRP and Stellar hash; recovered TRON address), and the device proves the amounts (Ledger trusted inputs, Trezor previous transactions). A protocol error therefore cannot produce a transaction different from the one displayed by Kyro: at worst the signature fails. Ledger: change recognized by its path (P1 `FF`), a single change output hidden. Trezor Stellar rebuilds the transaction itself from its fields; any difference from Kyro's makes verification fail. XRP on Trezor is not offered (the firmware does not give the public key before signing); TRON does not exist on Trezor.
- **Cardano and Zcash: same status (young code, simulated responses only).** Cardano (Ledger "Cardano ADA" app 7.x and ≥ 8, Trezor `CardanoSignTx*`): the device itself rebuilds and hashes the body from the elements Kyro gives it; Kyro requires that this hash be **its** transaction identifier and that the witness verify with the key derived from the registered account key, otherwise nothing is broadcast. The body Kyro builds is byte-for-byte identical to the bodies recorded by Ledger and Trezor in their tests (same hashes), and the signature recorded by Trezor is accepted. The CIP-20 memo is shown by the device only as a hash: Kyro displays the text in its dialog. A Ledger does not give the same Cardano addresses as the Kyro vault for the same phrase (Ledger's own derivation); a Trezor does (ICARUS). Zcash: Trezor only, each signature verified against the ZIP-244 digest computed by Kyro; not on Ledger (the app requires the complete previous transactions, shielded parts included, see IPC.md §2.3).
- **Trezor Safe 7 (THP protocol): see the next section.**

### Trezor Safe 7: THP encrypted channel and pairing

The Safe 7 speaks the **Trezor Host Protocol** (THP): an encrypted and authenticated channel between Kyro and the device, opened by a `Noise_XX_25519_AESGCM_SHA256` handshake (`snow` library, RustCrypto primitives), after a **pairing** done once per Kyro installation. Specification: `docs/common/thp/` in the trezor-firmware repository; cross-checked with python-trezorlib and Trezor Suite.

- **What THP provides.** Another program or an intermediary on the USB cable neither reads nor modifies the messages (addresses, transactions, signatures), and cannot impersonate the device to Kyro without having seen the code displayed by the device. The rest does not change: Kyro decodes and displays the transaction, the device shows it and has it confirmed, Rust verifies each signature and each address as for the other Trezors.
- **Pairing by code.** The device displays a 6-digit code; you type it into Kyro. Kyro proves via CPace (password-authenticated key exchange, Curve25519) that it knows the same code, without revealing it, and the device in turn proves that it did not choose it after the fact (commitment to its secret before Kyro's challenge). Wrong code or invalid proof: failure (`HW_PAIRING_FAILED`), nothing is saved. **Verify that the code really comes from your Trezor's screen** and that the device displays "Kyro Wallet". Kyro gives the device **only that fixed label**, never your computer's name (it would be displayed and kept by the device). Only `hw_open` can pair; the other operations answer `HW_PAIRING_REQUIRED`.
- **What is saved: `trezor-thp.json`**, next to the vault, **unencrypted** JSON (permissions restricted to the owner on Linux/macOS): **Kyro's static THP private key** (X25519, one per installation), and for each paired device its **static public key**, the **credential** it issued — a MAC by the device over Kyro's public key and the "Kyro Wallet" label —, its model and the date. No wallet key, no PIN, no passphrase, no address.
- **What someone who reads this file can do.** Present themselves to **your** Trezor as Kyro without going through the code again (on this computer or another, device plugged in); the device still asks to **confirm the connection** on its screen (Kyro never asks for "autoconnect"), then the PIN if it is locked; they can **sign nothing** without your confirmation on the device, but once connected and the device unlocked, they can read your public keys (privacy). They also learn the device's static public key (an identifier). Malicious software already running on your computer while Kyro is open does not need this file anyway. **What they cannot do**: steal funds, read private keys, bypass the device's screen.
- **Someone who can write it** can erase or replace the pairings (you will have to pair again), or put the key of a fake device in it: Kyro would then skip the code for that fake device, but it does not hold your keys, and Kyro always re-reads and verifies the device's keys and signatures (`HW_WRONG_DEVICE`, `HW_BAD_RESPONSE`).
- **Forgetting.** `hw_thp_forget` deletes a pairing or the whole file (and Kyro's key). This does **not** erase Kyro from the device's memory: to revoke on the device side (copied file, lost computer), reset the paired hosts from the Trezor (or reset the device), which invalidates all its credentials.
- **Device authenticity: not verified by Kyro.** THP authenticates the device through pairing (it is indeed the device whose screen you read), not through a manufacturer certificate: the device's static key is signed by no one. Trezor's authenticity check is a separate message (`AuthenticateDevice`), which also exists on Safe 3 and Safe 5: three X.509 certificate chains (Optiga chip in P-256, Tropic chip in Ed25519, MCU in ML-DSA-44) up to the root keys published by Trezor (`python/src/trezorlib/_root_keys.py`), plus a revocation list maintained by Trezor. Kyro does not implement it yet (it would need an X.509 parser, ML-DSA-44 — a young RustCrypto crate — and P-256 without the current `crypto-bigint 0.5`, which is under a RUSTSEC advisory). **Do the authenticity check in Trezor Suite** when you receive the device.
- **Residual risks.** Never tested against a real Safe 7 or the emulator (no Linux/macOS here): tested against **Trezor's device-side THP code** (the `trezor-thp` crate, the one in the firmware since 2.12.4), with packet losses and corruptions, and vectors from trezorlib and Trezor Suite. **The CPace step of the pairing is composed by Kyro** from curve25519-dalek primitives (no mature Rust library provides CPace or RFC 9380's Elligator2 directly; the official `trezor-thp` crate has no pairing, and the firmware's CPace is in Python on top of C trezorcrypto): curve25519-dalek's Elligator2 function, reachable only through `nonspec_map_to_curve` (deprecated API), gives 8·G, and Kyro divides the clamped X25519 scalar by 8 (exact identity, no hand-written field arithmetic). **Verified against python-trezorlib's CPace** on 4 fixed vectors and 200 random exchanges (fixed seed, host and device roles), re-checked with the Trezor Suite implementation, and rejection of low-order keys. It is not an audited CPace library. `snow`'s AES-GCM session keys are not wiped from memory when the channel closes.
- **C libraries.** The USB transport relies on hidapi (Ledger, C on Windows/macOS) and libusb (Trezor, C, LGPL-2.1+, statically linked), the standard routes; they run inside Kyro's process.

### Chains not supported on hardware wallets

Litecoin, Dogecoin, TRON, XRP, Cardano, Stellar and Monero: `HW_UNSUPPORTED`. Not offered, for protocol reasons ([docs/IPC.md](docs/IPC.md) §2.3): **Polkadot** (the Ledger app requires the `CheckMetadataHash` extension and an RFC-0078 metadata proof with each transaction, and ed25519 keys; Kyro signs in sr25519 without this extension, and Parity's library that builds the proof, `merkleized-metadata`, is not integrated: it would also be necessary to read the runtime's V15 metadata on each send), **Kaspa** (the app signs version 0 transactions with the same signature hash as Kyro and returns it, so the protocol is verifiable; but it spends from several `m/44'/111111'/a'/0|1/i` addresses: an extended-key hardware wallet account and the traversal of its addresses are needed, not yet written). The same rules would apply (native dialog, verification of each signature by Rust).

### Hedera on Ledger

- **An ED25519 account, different from the vault's.** The Ledger "Hedera" app (≥ 1.9.0) signs only with ED25519 keys `m/44'/3030'/0'/0'/n'`; the vault's Hedera account is ECDSA (`m/44'/3030'/0'/0/n`). An ED25519 key has no EVM address: Kyro **does not create** this account, it must have been created with this Ledger (Ledger Live, HashPack…). Kyro finds it on the mirror node **by its public key** (the returned key must be exactly ours, of type ED25519) and displays only its `0.0.x` identifier for receiving; as long as it does not exist, the public key (DER form) is shown with the warning that it is not an address.
- **Same chain of checks**: key re-read on the device before each signature; `TransactionBody` built and decoded by Kyro (same subset as the vault: one HBAR transfer, payer = our account); native window; the app itself decodes the body, displays accounts, amount, fees and memo, then signs the body bytes; Kyro verifies the ED25519 signature (`verify_strict`) and the signature pair (full 32-byte key) before and after broadcast.
- **A single copy** (a single consensus node): each copy would require a confirmation on the device. If that node temporarily refuses, rebuild the send. Body limited to 251 bytes (one APDU: short memo).
- **Residual risks.** Written from the app's code (LedgerHQ/app-hedera 1.9); **never run against a real device or Speculos**. The mirror node can hide the account (nothing is sent) or lie about its balance, as for the vault.

### TON on Ledger

- **A different wallet from the vault.** The Ledger "TON" app (≥ 2.1.0) uses Ledger Live's six-level path, `m/44'/607'/0'/0'/n'/0'`; the vault uses `m/44'/607'/n'`: the same phrase yields a different key, hence a different v4R2 address. The hardware wallet account is labeled as such; its address is recomputed by Kyro from the key (v4R2 wallet, **network wallet id**: standard 698983191 on mainnet, `0x4B59524F` on testnet like the vault — the app's "tag 1" request lets it be fixed, so the testnet → mainnet protection is the same).
- **The device rebuilds and displays the transfer.** Kyro does not send opaque bytes: it sends the app's structured request (`doc/TRANSACTION.md` of LedgerHQ/app-ton: wallet id, seqno, expiry, amount, recipient, bounce, mode, comment and its "hint"), the device rebuilds the v4R2 order cell, displays recipient, amount and comment, and signs its hash. Kyro compares this hash to **its own** hash of the cell (otherwise refused: the device would have signed something else), verifies the ed25519 signature (`verify_strict`), then re-verifies the signed message before broadcast. Never a "blind" signature (no payload without a hint).
- **Restrictions on Ledger**: comment in **printable ASCII, 120 characters at most** (app limit); without a comment, the empty body is inline (the form the app rebuilds); same rules as the vault for the rest (one message, mode 3 or 130, no internal `StateInit`, no tokens).
- **Residual risks.** Written from the app's code (LedgerHQ/app-ton 2.9) and `@ton-community/ton-ledger`; **never run against a real device or Speculos**. A format error would make the device or Kyro refuse the transfer (different hash), not sign something else.

### Sui, Aptos, Algorand, NEAR, Cosmos Hub on Ledger

- **Same addresses as the vault** for Sui, Aptos, Algorand and Cosmos Hub (same paths as Kyro: a Kyro phrase restored on a Ledger gives the same addresses). **NEAR: different account** — the Ledger NEAR app accepts only 5-level paths; Kyro uses Ledger Live's, `m/44'/397'/0'/0'/(n+1)'`, whereas the vault uses `m/44'/397'/n'`.
- **Same chain of checks** as the other chains: the key is re-read on the device and compared with the registered one before each signature and each address display; Rust decodes the transaction and displays it in the native window; the device displays then signs **the bytes built by wallet-core**; Rust verifies the signature (strict ed25519; Cosmos: DER converted, low-S) before assembling it, then re-verifies it before broadcast.
- **Cosmos Hub: amino JSON.** The Cosmos app does not sign SIGN_MODE_DIRECT; hardware wallet transactions are LEGACY_AMINO_JSON, and the signed JSON is produced by Kyro (canonical, sorted keys) from the decoded transaction. Memo limited to printable ASCII without `" \ < > &` (no escaping ambiguity between JSON encoders).
- **Residual risks.** Written from the official host libraries (`@mysten/ledgerjs-hw-app-sui`, `@ledgerhq/hw-app-aptos`, `@zondax/ledger-algorand`, `near-ledger`, `@zondax/ledger-cosmos-js`) and the apps' tests; **never run against a real device or Speculos**. A format error would make the device or Kyro refuse the transaction (signature that does not verify), not sign something else. Adding a chain to an existing account does not prove that it is the same device as for the other chains (only the same brand and the same account number).

## Automatic updates

Enabled by default (Settings → Security → "Automatic updates"), with no action on your part: Kyro checks the latest GitHub release in the background, downloads the package, and installs it **on close** (otherwise at the next startup); at the next startup, a small message says "Kyro updated to X".

- **Network**: only through Kyro's network layer (`NetClient::server_request`), **via Tor** when Tor is active (isolated circuits, `update` family), never a clear fallback; hosts `github.com` and `release-assets.githubusercontent.com` only, refused to the interface (`net_fetch`). The HTTP plugin of tauri-plugin-updater is **not** used (it would bypass Tor).
- **Signature**: the package (NSIS installer, `.app.tar.gz`, AppImage) must carry a valid minisign signature (Ed25519, BLAKE2b-prehashed) for the public key **compiled into the binary**. Verified at download, then **again** just before installation (a file modified on disk in the meantime is deleted). No unverified file is ever executed or copied.
- **No rollback**: only a **strictly newer** semver version is taken (no pre-release over a stable version). Since `latest.json` is not signed, Kyro also binds the version to the signed content: a version written in the signed file name (`Kyro_1.2.0_x64-setup.exe`) must be the announced one, and the signed timestamp must be newer than that of the last applied update (replay of an old signed package refused). **Limitation**: before the very first automatic update, and for the macOS archive (no version in its name), only the timestamp order protects: an old signed package that is **newer** than the last applied update could still be presented under a higher number (it would remain signed by Kyro).
- **Failures**: network, signature, disk: nothing changes, the error is logged; an installation attempted 3 times without success is abandoned.
- **Supported installations**: Windows installed by the NSIS installer (`uninstall.exe` next to the executable; `/S` mode on close, passive `/P` with restart at startup); macOS (`.app` bundle replaced, it must be writable by your account); Linux as AppImage (`$APPIMAGE`). MSI, `.deb` and `.rpm`: no automatic update (package manager). Development builds never update.
- **Signing key**: generated by `pnpm tauri signer generate`, kept outside the repository (and backed up offline), supplied to CI through the `TAURI_SIGNING_PRIVATE_KEY` secret ([docs/RELEASING.md](docs/RELEASING.md)). Someone who obtains this key **and** can publish a release could deliver code to all wallets: it is the project's most sensitive secret. Losing it prevents installed wallets from receiving updates (a version with a new key would have to be reinstalled by hand).

## Anonymous weekly count

Enabled by default (Settings → Privacy → "Anonymous weekly count"). Kyro collects no personal data; to estimate how many wallets are active, it downloads once a week a tiny file of its latest GitHub release (`ping.txt`, 4 bytes) and the public download counter of that file does the counting (`.github/workflows/stats.yml` publishes the totals on the `stats` branch).

- **When**: at most once per ISO week, ≈ 90 s after an unlock, only once Tor is ready (`weekly_count.rs`). The only local state is the last week sent (`weekly-count` in the data folder).
- **Network**: same path as the updater (`NetClient::server_request`, family `update`, hosts `github.com` → `release-assets.githubusercontent.com`), **Tor only**: with Tor off it is never sent, never in clear. A plain `GET`: no identifier, no version, no extra header, no body. Failures are dropped silently (retried at a later unlock of the same week).
- **What GitHub learns**: that some Kyro wallet was unlocked this week, from a Tor exit relay. Nothing links two weeks or two wallets together.

## Verifying a release

Binaries will be published with their SHA-256 fingerprints and a signature. To rebuild it yourself: see the *Build* section of the [README](README.md). Bit-for-bit reproducible builds are a goal, not yet a guarantee.
