# Kyro network requests

Kyro contacts **only** the servers below, and only for the stated reason. There is **no telemetry**, no automatic crash reporting, and no background update check.

The UI (webview) cannot reach any server: the CSP only allows Tauri's IPC channel, and a **navigation guard** (Rust) refuses any navigation outside the app's own pages (`tauri://localhost`, `http(s)://tauri.localhost`, the development server in debug) as well as any new window (`window.open`): a compromised page cannot exfiltrate data through `location.href = "https://…/?d=…"` (which would go out in cleartext, outside Tor). All requests go through the Rust command `net_fetch`, which:
- refuses any host that is not on this list (or among your custom servers **approved in a native window**, see below);
- accepts only HTTPS (the one exception: mempool's onion service listed below, over `http://` and **only through Tor**), and refuses redirects to a host that is not on the list; redirects are followed by Kyro itself (in Tor mode as well as clear mode) and an API key is **never** sent on to another host;
- caps the response at 5 MB and the duration at 20 s;
- caches (bounded: 128 responses, 16 MiB) and rate-limits (CoinGecko);
- goes **through the built-in Tor by default** (see "Modes" below).

## Modes: Tor (default) or clear

Kyro embeds a Tor client (Arti, from The Tor Project). It starts in the background when the app opens; its state is shown by the UI.

| | Tor mode (default) | Clear mode (explicitly turned off by you) |
|---|---|---|
| Your IP address | **Hidden**: the server sees the IP of a Tor exit relay. Your internet provider only sees that you use Tor. | Visible to every server contacted and to your internet provider (which sees the hostnames). |
| Request contents | Encrypted end to end with TLS up to the server (the exit relay only sees the hostname and the volume). | Encrypted with TLS. |
| Your public addresses, your transactions | **Always visible to the queried server**: Tor hides *who* you are on the network, not *what* you ask for. | Visible to the queried server, and associated with your IP. |
| Links between activities | Each family — **bitcoin**, **litecoin**, **dogecoin**, **zcash**, **bitcoincash**, **dash**, **tron**, **xrp**, **ton**, **stellar**, **cardano**, **near**, **sui**, **hedera**, **kaspa**, **polkadot**, **algorand**, **monero**, **cosmos**, **aptos**, **evm**, **solana**, **market** (CoinGecko), **swap** — uses its own isolated circuits: an exit relay or a server cannot link, through the circuit, your Bitcoin lookup and your Solana lookup. | All requests leave from the same IP. |
| Outage | **Fail closed**: if Tor is not ready within 60 s, the request fails (`TOR_UNAVAILABLE`) and **nothing is sent in cleartext**. No automatic fallback. | — |

Per server, in Tor mode: CoinGecko sees the cryptocurrencies and the currency requested; mempool, litecoinspace, TronGrid, the XRPL servers, TON Center, Horizon (Stellar), Koios (Cardano), AlgoNode (Algorand), FastNEAR (NEAR), the Sui GraphQL, the Hedera mirror node and nodes, the Kaspa API, Parity's Polkadot node, the Cosmos Hub LCDs, Aptos Labs, and the EVM and Solana RPCs see the addresses and transactions requested; the Monero node sees the blocks you download and the transactions you broadcast, **not your addresses** (see below); the swap APIs see the tokens, amounts and the recipient address — but none of them sees your IP, and two different families never share a circuit.

**Bitcoin in Tor mode: mempool's onion service.** In Tor mode, Rust automatically rewrites `https://mempool.space/…` to `http://mempoolhqx4isw62xs7abwphsq7ldayuidyx2v2oethdhhj6mlo2r6ad.onion/…` (same path). The connection stays **entirely inside the Tor network**: no exit relay is involved, so no relay sees the hostname or the volume, nor can any relay tamper with the traffic. The `http://` is not a weakening: an onion address *is* the service's public key, which the protocol authenticates, and the connection is encrypted end to end — which replaces TLS. This exception applies **only** to that specific onion address and **only through Tor**; any other `http://` URL remains refused, and any `.onion` address is refused in clear mode. Mempool still sees the addresses and transactions requested, but neither your IP nor that of an exit relay.

Source of the onion address: the `Onion-Location` HTTP header returned by https://mempool.space/ (verified on 2026-10-30, authenticated by mempool.space's TLS certificate): `Onion-Location: http://mempoolhqx4isw62xs7abwphsq7ldayuidyx2v2oethdhhj6mlo2r6ad.onion/`.

Switching back to clear mode is an explicit choice in Settings, confirmed in a **native system window** ("Turn Tor off?" (Désactiver Tor ?)): a compromised UI cannot turn Tor off without you. Your custom RPCs also go through Tor when it is enabled. Tor's data (consensus, guard state) is stored in the app folder (`tor/`).

Why the onion: `mempool.space` does not respond to Tor exit relays (timeout at the exit on all our attempts, 2026-10-30); its onion service does respond.

## Custom servers (Settings → Networks)

You can replace each chain's default server: Bitcoin (Esplora, Electrum or your Bitcoin Core node), Litecoin, Dogecoin, Bitcoin Cash and Dash (Esplora; for Dogecoin and Dash mainnet it replaces Komodo's ElectrumX servers, for Bitcoin Cash the public Fulcrum servers — a custom **Electrum** server is not yet accepted for these chains), TRON (java-tron HTTP API, like TronGrid; history requires TronGrid's `/v1` API: with a node alone, it is rejected with a clear message), XRP Ledger (rippled JSON-RPC), Cardano (Koios instance), Monero (`monerod` node, ideally your own, or a `.onion` address), each EVM chain, each Solana cluster (Cosmos Hub: not yet; its default servers are always used). **Kaspa: not yet** (the default public API only; a personal `kaspa-rest-server` will require the same network check, `networkName`). Common rules:
- **each new host is confirmed in a native system window before any request** ("New server": what it is for, `scheme://host:port`), whether to save it, test it, or read the certificate of an Electrum server. Without your approval, nothing goes out: no request, no DNS resolution, no connection to an address on your local network. A host that is already saved, or was authorized earlier in the session, is not asked about again; changing the port counts as a new host. If you did not enter the address yourself, refuse: a compromised interface could use it to exfiltrate data (the hostname itself can carry data) or probe your local network;
- a custom server is authorized **only for its own family** and goes through that family's **isolated Tor circuits**;
- it is verified at save time: it must be on the right network (Bitcoin, Litecoin, Dogecoin, Dash or TRON genesis; Bitcoin Cash: genesis **and** block 478,559 after the split, XRPL `network_id`, Cardano `networkmagic`, Monero `nettype` and block 0, `eth_chainId`, Solana genesis), otherwise it is rejected;
- as soon as it is configured, that chain's default server is **refused**: if your server goes down, Kyro shows an error (`SERVER_UNREACHABLE`) and **never falls back** to the default server — otherwise your addresses would go to the third party you precisely wanted to avoid;
- never credentials in a URL; plain `http://` is allowed only for a `.onion` address via Tor (the onion protocol authenticates the service and encrypts end to end) and, for Bitcoin Core only, for a local address;
- Bitcoin Core: the `.cookie` file is used only for a node that is **local or on your local network**, and is chosen in the system file picker (see [SECURITY.md](../SECURITY.md)); for a remote node, `rpcuser` / `rpcpassword`.

### Bitcoin via compact filters (BIP157/158) — `cbf` feature, disabled by default until reviewed

Kyro downloads **block filters** from Bitcoin peers, checks **on your machine** which blocks concern your scripts (BIP84 and BIP86, receiving and change, with a margin of unused addresses), then downloads only those blocks. No server learns your addresses.

| | Tor mode (default) | Clear mode (explicit choice) |
|---|---|---|
| Transport | **Only via Tor**: the P2P library can only go out through an internal SOCKS bridge (127.0.0.1, random port, active only during a sync or a broadcast) that accepts only the peers Kyro gave it and refuses everything else (including hostnames: no DNS request). `.onion` peers first, IPv4 peers via an exit relay only as a fallback. Fails closed: never a direct connection. | Direct connection to IPv4/IPv6 peers; `.onion` peers are ignored. |
| Peers | List provided by Kyro (peers serving filters, verified on 30/10/2026: testnet4 11 peers including 6 `.onion`; mainnet 14 peers including 11 `.onion`, out of a sample of 75) + yours. **No DNS seeds, no peer discovery.** | Same, IP only. |
| What a peer sees | A connection coming from Tor (neither your IP, nor anything to link you to your other activities); **which blocks you download in full**: a weak but real signal (a peer that sees the same requests repeated can guess that you have a transaction in those blocks). The filters themselves are identical for everyone and reveal nothing. | Same **and your IP**. |
| What your ISP sees | That you use Tor. | That you speak the Bitcoin protocol with these peers. |
| Broadcast | Your transaction is sent to a peer via Tor. | Sent directly to a peer. |

Honest limits:
- **No mempool**: a received payment appears only once mined; your own sends appear as "pending" until they are included.
- **Fees**: average of the fees actually paid (fee ÷ weight) in the last 3 blocks, with the peers' minimum relay fee as a floor. This is not a mempool estimate; you can always enter a manual rate.
- **First sync**: headers from the genesis block, then filters from your "birth date" (`birthHeight`); it can take several minutes via Tor. Recent headers and progress are kept in the app folder (`cbf/`).

Notes:
- With Electrum or Esplora, each lookup concerns one address: the server can group your addresses if it sees them in the same session. With Bitcoin Core, the node knows your xpub: use a **remote** node only if it belongs to you.
- Electrum: certificate validated normally (certificate authorities), or **pinned** by its SHA-256 fingerprint for self-signed servers (Kyro shows the fingerprint and asks you to confirm it). A certificate that is neither validated nor pinned is never accepted.
- A local Bitcoin Core node is reached over `http://` on your machine or local network, without Tor or a proxy.

## Interface navigation

Kyro's window shows only its own pages. Any other navigation (external link, `location.href`, form, `data:`, `file:`, `javascript:`) is refused by Rust, and `window.open` opens nothing. There is therefore **no clickable link** to an outside site in the app: documentation addresses are displayed as text.

## Adding a server

A PR that adds a host must change this page, `docs/IPC.md` and the Rust allowlist **at the same time**, and justify the need. A request not listed here is a security bug.
